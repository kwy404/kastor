Por que usar migrações de banco de dados

Todo projeto começa com alguém rodando um CREATE TABLE à mão. Funciona até a segunda pessoa entrar no time, ou até o primeiro deploy. A partir daí surgem as perguntas: qual coluna já existe em produção? Quem adicionou esse índice? Por que o staging tem uma tabela que o banco local não tem?

Migrações de banco de dados respondem a isso com uma regra simples: toda mudança de schema vira um arquivo, os arquivos ficam no repositório e são aplicados sempre na mesma ordem. O banco passa a ter histórico, como o código. Revisão de pull request, rollback de deploy e onboarding de pessoas novas ficam previsíveis.

No kastor o schema é escrito em TypeScript, e a CLI cuida de transformar diferenças entre esse schema e o banco em SQL. Você descreve o estado desejado, e a ferramenta escreve o passo para chegar lá.

O fluxo no dia a dia: migrate dev

O ciclo é sempre o mesmo. Você altera o arquivo de schema, roda um comando, revisa o SQL gerado e faz commit.

import { table, t, index } from 'kastor'

export const users = table('users', {
  id: t.id(),
  email: t.string(255).unique(),
  name: t.string().nullable(),
  createdAt: t.datetime().defaultNow(),
})

// New table added in this change
export const posts = table('posts', {
  id: t.uuid().primaryKey().defaultRandom(),
  title: t.string(200),
  published: t.boolean().default(false),
  authorId: t.int().references(() => users.id, { onDelete: 'cascade' }),
}, { indexes: (p) => [index(p.authorId)] })

npx kastor migrate dev --name add_posts

O comando lê o kastor.config.ts, compara o schema com o banco de desenvolvimento ao vivo, escreve kastor/migrations/<timestamp>_add_posts/migration.sql e aplica esse arquivo. O resultado é SQL comum, que você pode ler na revisão de código:

CREATE TABLE "posts" (
  "id" uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  "title" varchar(200) NOT NULL,
  "published" boolean NOT NULL DEFAULT false,
  "authorId" integer NOT NULL REFERENCES "users" ("id") ON DELETE CASCADE
);
CREATE INDEX "posts_authorId_idx" ON "posts" ("authorId");

Algumas boas práticas que evitam dor de cabeça:

  • Dê nomes descritivos: add_posts, users_add_role, drop_legacy_tokens. O nome aparece no histórico para sempre.
  • Faça uma mudança lógica por migração. Fica mais fácil revisar e entender o que deu errado.
  • Faça commit da pasta kastor/migrations no mesmo pull request que altera o schema e o código que usa a mudança.
  • Nunca edite uma migração já aplicada em outro ambiente. Crie uma nova.

Produção e CI: migrate deploy e migrate status

Em produção você não quer que nenhuma ferramenta invente SQL. Por isso existe um comando separado: migrate deploy só aplica migrações que já estão no repositório e ainda não rodaram naquele banco. Ele não compara schema, não pergunta nada e não gera arquivo.

O lugar certo para ele é uma etapa do pipeline antes de a nova versão da aplicação receber tráfego. Um exemplo com GitHub Actions:

jobs:
  migrate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
      - run: npm ci
      - run: npx kastor migrate status
        env:
          DATABASE_URL: ${{ secrets.DATABASE_URL }}
      - run: npx kastor migrate deploy
        env:
          DATABASE_URL: ${{ secrets.DATABASE_URL }}

O migrate status mostra quais migrações já foram aplicadas e quais estão pendentes. É útil no log do CI e também localmente, quando você puxa a branch de alguém e quer saber se o banco está atrasado.

Rode migrate deploy em um único lugar por deploy. Se cada instância da aplicação tentar migrar ao iniciar, várias vão competir pelo mesmo banco ao mesmo tempo.

Renomeações sem perder dados

Para uma ferramenta que compara dois estados, renomear uma coluna parece igual a apagar uma coluna e criar outra. Ferramentas ingênuas geram exatamente isso, e os dados da coluna antiga somem.

O migrate dev do kastor detecta esse padrão. Quando uma coluna desaparece e outra compatível aparece na mesma tabela, ele pergunta se é uma renomeação em vez de gerar o DROP. Responda que sim e o arquivo terá um rename, preservando os dados. O mesmo vale para tabelas.

Se você só quer mudar o nome no código e manter o nome no banco, nem precisa de migração: use .map('nome_antigo') na coluna. O TypeScript enxerga o nome novo e o banco continua com o antigo.

Mudanças destrutivas seguras: expandir e contrair

Renomear dentro de uma migração resolve o banco, mas não resolve o deploy. Durante alguns segundos ou minutos, a versão antiga da aplicação ainda está rodando e procura a coluna pelo nome antigo. Para mudanças que quebram compatibilidade, use o padrão expandir e contrair (expand and contract), em etapas separadas:

  1. Expandir. Adicione a coluna nova como .nullable() ou com .default(). Gere a migração e faça deploy. Nada quebra, porque a versão antiga ignora a coluna.
  2. Escrever nas duas. Publique código que grava na coluna antiga e na nova, e lê da antiga.
  3. Preencher. Copie os dados existentes em lotes, com um script que usa db.$execute. Lotes pequenos evitam travar a tabela por muito tempo.
  4. Trocar a leitura. Publique código que lê da coluna nova.
  5. Contrair. Remova a coluna antiga do schema, gere a migração e faça deploy. Se precisar, torne a coluna nova obrigatória nessa mesma etapa.
import { db } from '../src/db/client'

// Copy data in small batches until nothing is left to update
let affected = 0
do {
  affected = await db.$execute`
    update users set "displayName" = name
    where id in (
      select id from users
      where "displayName" is null and name is not null
      limit 1000
    )
  `
} while (affected > 0)

await db.$disconnect()

Parece muito trabalho para trocar um nome, e para uma tabela pequena em um projeto pessoal talvez seja. Mas em tabelas grandes ou com várias instâncias da aplicação, é o que separa um deploy tranquilo de um incidente. A mesma lógica vale para trocar o tipo de uma coluna, dividir uma tabela ou tornar obrigatória uma coluna que era opcional.

Revise também o SQL gerado pensando em bloqueios. Criar um índice ou mudar o tipo de uma coluna em uma tabela com milhões de linhas pode travar escritas enquanto o banco trabalha. Teste essas migrações em uma cópia com volume parecido com o de produção e programe o deploy para um horário de pouco movimento.

db push, db pull e migrate reset

Três comandos completam o conjunto, cada um com um uso bem definido.

ComandoQuando usarGera arquivo?
db pushProtótipos e experimentos locaisNão
db pullAdotar o kastor em um banco que já existeGera o schema em TypeScript
migrate resetRecomeçar o banco local do zeroNão

db push sincroniza o banco com o schema sem criar migração. É ótimo nas primeiras horas de um projeto, quando o modelo muda a cada dez minutos. Quando o schema estabilizar, rode o primeiro migrate dev e não use mais db push em bancos compartilhados.

db pull lê as tabelas, colunas, índices e chaves estrangeiras de um banco existente e escreve um arquivo de schema em TypeScript. Revise o resultado, acrescente as relações no cliente e siga com migrações normais. É o caminho para trazer um sistema legado para um ORM para TypeScript sem reescrever nada.

migrate reset apaga e recria o banco de desenvolvimento aplicando todas as migrações. Junto com db seed, deixa o ambiente local em um estado conhecido. Nunca aponte esse comando para produção.
