What a database migration is

Your application code and your database schema change together. When you add a role field to the user model, the users table needs a matching column, and every database that runs your code needs it too: your laptop, a teammate's laptop, the CI database, staging and production.

A migration is the unit that carries that change. It is a small file of SQL statements, such as CREATE TABLE or ALTER TABLE ... ADD COLUMN, with a timestamp in its name so migrations always run in the same order. Applying all migrations from an empty database rebuilds the current schema exactly. Applying only the new ones upgrades an existing database without touching its data.

In kastor, the source of truth for the shape you want is your TypeScript schema, written with table() and the t column builders. The migration files are the source of truth for how each database got there. You need both.

Schema drift and why it hurts

Schema drift is when two databases that should match do not. It usually starts innocently: someone adds an index by hand in production to fix a slow page, or runs an ALTER TABLE from a SQL console during an incident, or a feature branch changes a column and is then abandoned after its change was applied to staging.

Drift causes bugs that are hard to reproduce. A query works locally and fails in production because a column is nullable in one place and not the other. A migration that runs fine in CI fails on deploy because the index it creates already exists.

The cure is discipline more than tooling: every schema change goes through a migration file, and no one changes a shared database by hand. If an emergency fix does happen in production, write a migration that matches it right away, so the history and reality agree again.

The migration workflow, step by step

The kastor workflow has four commands. First point kastor.config.ts at your schema and a migrations folder:

import { defineConfig } from 'kastor'
import { postgres } from 'kastor/postgres'
import pg from 'pg'

export default defineConfig({
  schema: './src/db/schema.ts',
  adapter: () => postgres(new pg.Pool({ connectionString: process.env.DATABASE_URL })),
  migrations: './kastor/migrations',
})

The day to day loop:

  1. Change the schema in src/db/schema.ts. Types update as you type, there is no generate step.
  2. Run migrate dev with a descriptive name. kastor diffs the TypeScript schema against your local database, writes kastor/migrations/<timestamp>_<name>/migration.sql and applies it.
  3. Read the SQL and commit it together with the schema change, in the same pull request, so reviewers see both.
  4. Run migrate deploy in CI or on release. It applies pending migrations in order and never generates anything new.
npx kastor migrate dev --name add_posts
git add src/db/schema.ts kastor/migrations
npx kastor migrate status
npx kastor migrate deploy

migrate status tells you which migrations are applied and which are pending for the database in DATABASE_URL.

Only run migrate dev against a development database. It is the command that creates new files and may ask questions. Shared environments get migrate deploy, which only applies what is already committed.

Readable SQL files and the migrations table

Each migration is a folder with a single migration.sql inside. It is ordinary SQL for your database, so you can read it in review and run it in your head:

CREATE TABLE "posts" (
  "id" uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  "title" varchar(200) NOT NULL,
  "body" text,
  "published" boolean NOT NULL DEFAULT false,
  "authorId" integer NOT NULL REFERENCES "users" ("id") ON DELETE CASCADE
);

CREATE INDEX "posts_authorId_idx" ON "posts" ("authorId");

Because the file is plain SQL, you are allowed to edit it before it leaves your machine. Keep the file and the TypeScript schema consistent: if you add something by hand that the schema does not know about, the next diff may try to remove it.

To know what has been applied, kastor keeps a bookkeeping table named _kastor_migrations in each database. Every row records the migration folder name, a checksum of its migration.sql and when it was applied. migrate deploy compares the folders on disk with those rows and runs only what is missing. The checksum is why you should treat a migration as frozen once a shared database has applied it: fix mistakes with a new migration instead of rewriting history.

Renames and destructive changes

The riskiest diff is a rename. To a naive differ, renaming name to fullName looks like "drop column name, add column fullName", which deletes every value in that column. When migrate dev sees a column vanish and a compatible one appear in the same table, it asks whether you renamed it. Answer yes and the migration uses a rename statement, so the data stays.

If you only want a nicer property name in TypeScript, skip the migration entirely: keep the database column and map it with .map('name') on the new property.

Expand and contract

Some changes are destructive no matter what: dropping a column, making a column NOT NULL, shrinking a type, or splitting one column into two. During a deploy, old and new versions of your code run side by side for a while, so a single step change can break the version that is still serving traffic. The safe pattern is expand and contract:

  1. Expand. Add the new column as nullable. Old code ignores it.
  2. Write both. Ship code that writes the old and the new column.
  3. Backfill. Fill the new column for existing rows, in the migration or in batches for big tables.
  4. Switch reads to the new column and deploy.
  5. Contract. In a later migration, add the NOT NULL constraint and drop the old column.
ALTER TABLE "users" ADD COLUMN "displayName" varchar(100);

-- added by hand: backfill before the column becomes required
UPDATE "users"
SET "displayName" = COALESCE("name", split_part("email", '@', 1))
WHERE "displayName" IS NULL;

It takes two or three deploys instead of one, but no request fails and no data disappears.

db push for prototyping, db pull for existing databases

CommandWhat it doesUse it when
migrate devWrites a SQL file and applies itThe change will reach anyone else
db pushSyncs the schema directly, no fileYou are prototyping on a throwaway database
db pullIntrospects a database into a TypeScript schema fileYou are adopting kastor on an existing database
migrate deployApplies committed migrationsCI, staging and production

db push is fast because it skips the history. That is exactly why it does not belong on shared databases: nothing records what changed. A good habit is to push freely while an idea is taking shape, then reset your local database and create one clean migration with migrate dev once the schema settles.

db pull is the starting point for an existing project. It reads the live tables, columns, indexes and foreign keys and writes a schema file you can tidy up. From then on, every schema change goes through migrate dev like in any other project.

Running migrations in CI

In CI you want two things: tests run against a schema built only from committed migrations, and production receives exactly those migrations. Both come down to migrate deploy.

name: deploy
on:
  push:
    branches: [main]
jobs:
  migrate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
      - run: npm ci
      - run: npx kastor migrate status
        env:
          DATABASE_URL: ${{ secrets.DATABASE_URL }}
      - run: npx kastor migrate deploy
        env:
          DATABASE_URL: ${{ secrets.DATABASE_URL }}

A few rules keep this boring, which is what you want:

  • Run migrations as their own step before the new application version starts, and only once per deploy, not from every server instance on boot.
  • Use a database user that is allowed to change the schema for this step, and a more limited user for the running app.
  • In the test job, start an empty database, run migrate deploy, then run the tests. If a migration only works on your laptop, this is where you find out.
  • Keep every migration backward compatible with the code that is currently live, using expand and contract for anything destructive.
