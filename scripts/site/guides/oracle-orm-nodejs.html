oracledb thin mode: no Instant Client required

For years, connecting Node.js to Oracle meant installing Instant Client on every developer machine, CI runner and container image. Current releases of oracledb default to thin mode, a pure JavaScript implementation of the network protocol. A normal npm install is all you need, and the same image builds on Linux, macOS and Windows.

kastor uses whatever driver instance you give it and ships no driver of its own. You create an oracledb pool and pass it to the oracle adapter from kastor/oracle. Thin mode covers ordinary application work: queries, writes, transactions, LOBs and JSON. Thick mode, enabled by calling initOracleClient(), is only needed for a short list of advanced features described in the node-oracledb documentation. Thin mode also needs a reasonably recent database release, so check the driver docs if you connect to a very old server.

npm install kastor oracledb
docker run -d --name oracle -p 1521:1521 -e ORACLE_PASSWORD=$ORACLE_ADMIN_PASSWORD -e APP_USER=app -e APP_USER_PASSWORD=$ORACLE_PASSWORD gvenzl/oracle-free:23-slim
docker logs -f oracle

A local Oracle with FREEPDB1

The gvenzl/oracle-free images package Oracle Database Free for containers and are the usual choice for local development and CI. The command above sets the admin password and creates an application user named app. That user lives in FREEPDB1, the pluggable database that ships with Oracle Database Free.

The detail that trips people up is the service name. Oracle Database Free runs a container database with pluggable databases inside it. Your tables belong in the pluggable one, so the connect string is localhost:1521/FREEPDB1, not FREE. Connecting to the wrong service gives you ORA-01017 for a user that only exists in the PDB, or ORA-12514 when the listener does not know the service.

The first start takes a while because the database initializes its files. Follow the logs and wait for the line saying the database is ready before you run migrations. In CI, use the container health check or poll with npx kastor doctor until it succeeds.

Create the pool and the client

Pool creation in oracledb is asynchronous, so create the pool once at startup and reuse it. The pool settings that matter most are poolMin and poolMax: keep the maximum in line with what your database user and server sessions allow.

import oracledb from 'oracledb'
import { kastor, one, many } from 'kastor'
import { oracle } from 'kastor/oracle'
import { users, posts } from './schema'

const pool = await oracledb.createPool({
  user: process.env.ORACLE_USER ?? 'app',
  password: process.env.ORACLE_PASSWORD,
  connectString: process.env.ORACLE_CONNECT ?? 'localhost:1521/FREEPDB1',
  poolMin: 1,
  poolMax: 10,
})

export const db = kastor({
  adapter: oracle(pool),
  schema: { users, posts },
  relations: ({ users, posts }) => ({
    users: { posts: many(posts) },
    posts: { author: one(users, { fields: ['authorId'], references: ['id'] }) },
  }),
})

Call await db.$disconnect() on shutdown so the pool closes its sessions. For Oracle Autonomous Database, thin mode connects with the wallet or connection string from the cloud console; the node-oracledb docs list the options, and kastor only sees the resulting pool.

Identity columns, booleans, dates and identifier case

Oracle has a few behaviors that differ from other databases. kastor smooths over the type mapping, but some rules come from the database itself.

  • Identity columns. t.id() becomes an identity column, the native auto increment of modern Oracle releases. You do not create sequences or triggers by hand, and created rows come back with their generated id.
  • Booleans. Recent releases have a native BOOLEAN type, while older ones store flags as numbers. Either way, a t.boolean() column reads and writes JavaScript true and false.
  • Dates. t.datetime() values are Date objects. t.date() values are 'YYYY-MM-DD' strings, which avoids time zone shifts on calendar dates. Remember that Oracle DATE also carries a time of day, so ad hoc SQL comparisons on legacy DATE columns may need TRUNC.
  • Empty strings are NULL. Oracle treats '' as NULL. Writing an empty string into a required column raises ORA-01400, reported as NOT_NULL_VIOLATION. Validate input or make the column nullable.

Identifier case

Oracle folds unquoted names to upper case. kastor quotes identifiers, so a table declared as users is created as lower case "users". Application code never notices, but ad hoc SQL in SQL Developer or SQL*Plus must quote the name. If your team prefers upper case names for ad hoc work, or you map an existing schema, declare them in upper case and keep readable field names with .map().

import { table, t } from 'kastor'

export const customers = table('CUSTOMERS', {
  id: t.id().map('CUSTOMER_ID'),
  email: t.string(255).unique().map('EMAIL'),
  active: t.boolean().default(true).map('IS_ACTIVE'),
  signedUpOn: t.date().map('SIGNED_UP_ON'),
})

Older releases limit identifiers to 30 bytes, while recent ones allow much longer names. If you target an old server, keep table, column and index names short.

Pagination, MERGE upserts and JSON includes

The Oracle dialect compiles the same query API you use on every other database into Oracle SQL:

  • take and skip become OFFSET ... ROWS FETCH FIRST ... ROWS ONLY, the row limiting clause of modern Oracle. Always pass orderBy with offset pagination, and use findPage for cursor pagination on large tables.
  • upsert compiles to MERGE, Oracle's statement for insert or update in one step. Keep a unique constraint on the key and handle UNIQUE_VIOLATION if two requests may upsert the same key at the same time.
  • Nested include trees load through JSON_ARRAYAGG and JSON_OBJECT, so a call with includes runs as one statement per root call rather than one per parent row.
  • Filters with mode: 'insensitive' compare lower cased values, which works the same on every Oracle collation setting.

Migrations and transactions on Oracle

Point kastor.config.ts at your schema file and at an adapter that builds the oracledb pool, as described in the API reference. Then npx kastor migrate dev --name init diffs the TypeScript schema against FREEPDB1, writes a migration file and applies it. A first migration looks roughly like this:

CREATE TABLE "users" (
  "id" NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  "email" VARCHAR2(255) NOT NULL UNIQUE,
  "name" VARCHAR2(255)
);

One Oracle rule shapes how you write migrations: every DDL statement commits implicitly. If the third statement of a migration fails, the first two stay applied. Keep migrations small, one logical change each, and test them against a copy of production data before running npx kastor migrate deploy. For an existing schema, npx kastor db pull writes the TypeScript schema from the live database, and the migrations guide covers the rest of the workflow.

Data changes are different: DML is fully transactional. db.$transaction(async (tx) => ...) runs on one pooled session and rolls back if the callback throws, and the array form runs a fixed list of queries atomically. Oracle defaults to read committed with consistent reads, so readers never block writers. It also supports serializable, which raises ORA-08177 when it cannot serialize your transaction; kastor reports that as SERIALIZATION_FAILURE, and the right response is to retry the whole transaction.
