How Prisma works, and why it is a valid trade-off

Prisma has a clear model. You describe your data in schema.prisma using the Prisma Schema Language. Running prisma generate reads that file and produces a client tailored to your models, with types for every query. Queries are executed by Prisma's query engine, which historically ran as a separate component next to your Node.js process; recent Prisma versions have been moving that work into TypeScript, so check the docs for the version you use.

This design has real strengths. The schema file is compact and readable by people who do not write TypeScript. The generated client is fully typed. Tooling such as migrations, introspection and Prisma Studio all work from the same file. Many teams ship production apps on it and are happy.

The cost is a build step between your schema and your code. If you are looking for a Prisma alternative without codegen, you most likely want to remove that step while keeping the query style you already know. That is the gap kastor is designed for.

What changes when the schema is plain TypeScript

In kastor, the schema is a TypeScript module. Types are inferred from it by the compiler, the same way types flow from any other TypeScript value. In practice that changes four things:

  • No generate step in CI. Your pipeline installs dependencies, type checks and runs npx kastor migrate deploy. There is no client to build and no postinstall hook to keep working.
  • No stale client. A classic surprise with generated clients is pulling a branch with a new column and seeing type errors until someone regenerates. With inference, the types are always the schema you have checked out.
  • Editor feedback as you type. Add slug: t.string(120).unique() to a table and the next line of code can already filter on slug, with autocomplete.
  • No separate engine. kastor compiles queries in TypeScript and sends them through the driver you installed (pg, mysql2, better-sqlite3, mssql and others). Bundlers and serverless platforms see a regular package.

What you give up is the dedicated schema language. Your models are TypeScript, so non TypeScript readers have to read code, and the schema file follows your formatter instead of its own.

Familiar concepts, side by side

kastor's query API is intentionally familiar, so most concepts map one to one. The main naming difference: the accessor is the key you give the table in the schema object, so prisma.user becomes db.users when you export the table as users. A schema written by db pull names each export after the database table in camelCase, so a Prisma table called User comes back as user until you rename it.

Here is a typical pair of models written as kastor tables, with the Prisma attribute noted on each line:

import { table, t } from 'kastor-orm'
import type { InferSelect, InferInsert } from 'kastor-orm'

export const users = table('users', {
  id: t.id(),                              // Int @id @default(autoincrement())
  email: t.string(255).unique(),           // String @unique
  name: t.string().nullable(),             // String?
  createdAt: t.datetime().defaultNow(),    // DateTime @default(now())
})

export const posts = table('posts', {
  id: t.id(),
  title: t.string(200),
  published: t.boolean().default(false),  // Boolean @default(false)
  // authorId Int, with onDelete: Cascade on the @relation
  authorId: t.int().references(() => users.id, { onDelete: 'cascade' }),
})

// Replaces the generated Prisma types
export type User = InferSelect<typeof users>
export type NewUser = InferInsert<typeof users>

Relations live on the client, where posts Post[] becomes many(posts) and the @relation attribute becomes one(...):

import pg from 'pg'
import { kastor, one, many } from 'kastor-orm'
import { postgres } from 'kastor-orm/postgres'
import { users, posts } from './schema'

export const db = kastor({
  adapter: postgres(new pg.Pool({ connectionString: process.env.DATABASE_URL, max: 5 })),
  schema: { users, posts },
  relations: ({ users, posts }) => ({
    users: { posts: many(posts) },
    posts: { author: one(users, { fields: ['authorId'], references: ['id'] }) },
  }),
})

Queries look the same on purpose

If your team knows Prisma, most query code reads the same. Filters, nested includes, nested writes and atomic updates use the same vocabulary.

import { isKastorError } from 'kastor-orm'
import { db } from '../db/client'

// Before: prisma.user.findMany({ where: { email: { contains: 'acme' } }, include: { posts: true } })
export const listTeam = () =>
  db.users.findMany({
    where: { email: { contains: 'acme', mode: 'insensitive' } },
    include: { posts: { where: { published: true }, take: 10 } },
  })

// Before: prisma.user.upsert({ where, create, update })
export const saveUser = (email: string, name: string) =>
  db.users.upsert({ where: { email }, create: { email, name }, update: { name } })

// Before: Prisma.PrismaClientKnownRequestError with code P2002
export async function register(email: string) {
  try {
    return { user: await db.users.create({ data: { email } }) }
  } catch (e) {
    if (isKastorError(e) && e.code === 'UNIQUE_VIOLATION') return { error: e.message, hint: e.hint }
    throw e
  }
}

Two differences are worth knowing. Error codes are readable names such as UNIQUE_VIOLATION and FOREIGN_KEY_VIOLATION instead of numbered codes, and every error carries a hint, with the original driver error kept as cause. Nested includes load in one query per root call on every SQL adapter, built with JSON aggregation, and in one aggregation on MongoDB; open the playground to see the exact SQL for each database.

Moving an existing Prisma project

You do not need a big rewrite. The safest path keeps both ORMs running against the same database until the last query moves.

  1. Install kastor and the driver next to Prisma, for example npm install kastor-orm pg.
  2. Run npx kastor import prisma --config. It reads schema.prisma and writes src/db/schema.ts with the same table, column and constraint names Prisma Migrate created, plus kastor.config.ts for your datasource. Read the report it prints: it lists every field whose behavior differs, such as @updatedAt. (npx kastor db pull is the alternative that reads the live database instead.)
  3. Run npx kastor migrate baseline --from-prisma prisma/migrations. It records the database as it is and keeps the Prisma migration history, without changing a table. Then npx kastor migrate dev should report that everything is already in sync. From here on, kastor owns migrations: stop running prisma migrate.
  4. Move queries module by module. Start with read paths, then writes. Tests that already cover a module tell you when it is done.
  5. Remove Prisma once nothing imports it, along with prisma generate in CI and postinstall.
npm install kastor-orm pg
npx kastor import prisma --config
npx kastor migrate baseline --from-prisma prisma/migrations
npx kastor migrate dev

The step by step Prisma migration guide shows the generated schema, the report and every Prisma Client call next to its kastor version.

While both clients run, each one has its own connection pool. Lower the pool sizes so the sum stays under your database's connection limit, which matters most on small managed PostgreSQL plans.

Which one fits your project

Stay on Prisma if your team values a dedicated schema file, relies on its ecosystem of integrations, or simply has no pain with the generate step. A working setup is worth a lot.

Consider kastor if the generate step causes friction in CI, monorepos or serverless builds, if you want types to update as you type, or if you need SQL Server, Oracle and MongoDB behind the same API. The TypeScript ORM guide walks through a full project, and the comparison on the home page lists more details.
