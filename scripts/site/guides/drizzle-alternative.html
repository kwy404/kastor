The same starting point: a schema in TypeScript

Drizzle helped popularize an idea that kastor shares: the schema is ordinary TypeScript, and types are inferred from it by the compiler. There is no schema language, no generate step and no generated client to keep in sync. If you are already happy with that model, you do not need to give it up.

So why look for a Drizzle alternative at all? Usually because of the other choices a tool makes on top of that idea: how queries are written, how one schema works across databases, how migrations treat existing data and what you see when something fails. Drizzle and kastor make different choices here. Neither is wrong, and this guide tries to describe both fairly so you can pick for your project.

Where the trade-off differs

Drizzle's core query API is SQL-like: you compose select, from, where and joins in TypeScript, and it also offers a relational query API for loading nested data. Its schema uses dialect specific builders such as pgTable and mysqlTable, which give direct access to each database's native types. That is a good fit for developers who think in SQL and want the code to mirror it.

kastor starts from the other end:

  • The object API is the main API. findMany, where, include, select and nested writes cover everyday work, and nested includes load in one query per root call on every SQL database, using JSON aggregation.
  • One schema for every dialect. The same table() and t builders work for PostgreSQL, MySQL, SQLite, SQL Server, Oracle and MongoDB. When you need a specific database type, .nativeType('varchar(64)') sets it on one column.
  • Migrations that ask before dropping. migrate dev diffs the TypeScript schema against the live database, writes a SQL file, applies it and asks when a change looks like a rename.
  • Readable errors. Driver errors become a KastorError with a stable code and a hint that suggests the fix.

The cost on kastor's side: when you want to hand write a complex query, you reach for raw SQL through db.$sql instead of a SQL-like builder.

One schema, nested includes

A kastor schema does not import anything dialect specific. The adapter decides the database, so the same file serves a PostgreSQL app and an SQLite test suite.

import { table, t, index } from 'kastor'

export const users = table('users', {
  id: t.id(),
  email: t.string(255).unique(),
  name: t.string().nullable(),
})

export const posts = table('posts', {
  id: t.id(),
  title: t.string(200),
  published: t.boolean().default(false),
  authorId: t.int().references(() => users.id, { onDelete: 'cascade' }),
  createdAt: t.datetime().defaultNow(),
}, { indexes: (p) => [index(p.authorId)] })

export const comments = table('comments', {
  id: t.id(),
  body: t.text(),
  postId: t.int().references(() => posts.id, { onDelete: 'cascade' }),
})

Queries describe the shape you want back. Each level of include can filter, sort, limit, select and include further on its own, and the result type mirrors the arguments.

import { db } from './db/client'
// relations: users.posts = many(posts), posts.author = one(users, ...), posts.comments = many(comments)

const feed = await db.users.findMany({
  where: { posts: { some: { published: true } } },
  include: {
    posts: {
      where: { published: true },
      orderBy: { createdAt: 'desc' },
      take: 3,
      include: { comments: { take: 5 } },
    },
    _count: { select: { posts: true } },
  },
})

// feed[0].posts[0].comments is typed, and so is feed[0]._count.posts
const preview = db.posts.findMany({ include: { author: true } }).toSQL()

toSQL() returns the statements without running them, which is handy in tests and code review. Open the playground to see the exact SQL for each database.

Migrations and renames

Both tools generate SQL migration files from the TypeScript schema, and both can push a schema directly while prototyping. In kastor, the commands live in one CLI:

npx kastor migrate dev --rename comments.body:content --name rename_body_to_content
npx kastor migrate deploy
npx kastor db push

migrate dev compares the schema with the live database, writes kastor/migrations/<timestamp>_<name>/migration.sql and applies it. When a column disappears and a compatible one appears in the same table, it asks whether you renamed it, so the data stays. You can also answer up front with --rename table.old:new, as in the first line, which is what scripts and other non interactive shells need; without an answer there, kastor stops instead of guessing. Add --create-only to write the file without applying it, so you can edit the SQL first. migrate deploy applies pending files in CI and production without generating anything. The migrations guide covers team workflows and safe destructive changes.

Errors you can act on

Every driver reports constraint failures differently: PostgreSQL uses SQLSTATE codes, MySQL numeric error numbers, SQL Server and Oracle their own. kastor maps them to one set of codes, so the same handler works on every database.

import { isKastorError } from 'kastor'
import { db } from '../db/client'

export async function addComment(postId: number, body: string) {
  try {
    return await db.comments.create({ data: { postId, body } })
  } catch (e) {
    if (isKastorError(e) && e.code === 'FOREIGN_KEY_VIOLATION') {
      // e.message explains the failure in plain English, e.hint suggests the fix
      throw new Error(`Post ${postId} does not exist`)
    }
    throw e
  }
}

Other codes include UNIQUE_VIOLATION, NOT_NULL_VIOLATION, SERIALIZATION_FAILURE, DEADLOCK and TIMEOUT. The original driver error stays available as e.cause, and details such as the constraint name sit in e.meta, so you lose nothing by using the mapped code.

Trying kastor in an existing Drizzle project

You can evaluate kastor without touching your Drizzle code. Both tools take a driver instance you create, so they can share the same database while you compare.

  1. Install kastor next to your current setup. You already have the driver, for example pg or better-sqlite3.
  2. Run npx kastor init and point kastor.config.ts at a development database.
  3. Run npx kastor db pull to introspect the tables Drizzle created into a kastor schema file. It replaces the starter schema that init wrote (after asking) and guesses relations from the foreign keys. Review the names and the relations.
  4. Port one read path, ideally one with nested data, and compare the code, the types you get and the statements from toSQL().
  5. Keep one migration owner. While you evaluate, let drizzle-kit keep managing the schema. Only hand migrations over once you decide to switch for real.

Give each client its own small pool so the total stays under your database's connection limit. If the comparison does not convince you, delete the kastor files and nothing else has changed.

How to choose

Choose Drizzle if you think in SQL, want queries that read like the statements they produce, and value direct access to each dialect's native types. Its community and integrations are a real advantage.

Choose kastor if you prefer describing results as objects, want the same schema and API on SQL Server, Oracle or MongoDB as on PostgreSQL, and like migrations and errors that explain themselves. If you are unsure, port one module of your app and compare the code side by side. The TypeScript ORM guide is a good place to start, and the database list shows every adapter.
