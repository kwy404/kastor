How kastor fits into a Worker

Cloudflare D1 is a serverless database built on SQLite and reached from Workers through a binding: an object Cloudflare injects into your Worker's env. There is no connection string, no pool and no TCP socket. That changes how an ORM has to be wired, and it is why kastor has a dedicated d1 adapter from kastor-orm/d1 that takes the binding directly.

Everything else is the regular kastor API. The schema is the same TypeScript you would write for SQLite or PostgreSQL, queries compile with the SQLite dialect, and nested include trees load in one statement per call through SQLite JSON functions. Nothing is generated at build time and no query engine is bundled into the Worker, which keeps the script small.

Create the database and the wrangler.toml binding

Create the database with wrangler, then copy the id it prints into wrangler.toml. The binding name is the property your code reads from env.

npm install kastor-orm
npm install -D wrangler better-sqlite3
npx wrangler d1 create app-db
npx wrangler types

name = "app"
main = "src/index.ts"
compatibility_date = "2026-09-01"

[[d1_databases]]
binding = "DB"
database_name = "app-db"
database_id = "paste-the-id-from-wrangler-d1-create"
migrations_dir = "migrations"

npx wrangler types writes a declaration file with an Env interface that includes DB: D1Database, so the binding is typed in your handler. Run it again whenever you change bindings.

Create the client inside fetch

The binding exists only inside a request: Cloudflare passes env to fetch, not to module scope. So build the client per request with d1(env.DB). This costs very little, since the adapter wraps the binding and opens nothing. A small factory keeps the schema and relations in one place.

import { kastor, one, many } from 'kastor-orm'
import { d1 } from 'kastor-orm/d1'
import { users, posts } from './db/schema'

function createDb(binding: D1Database) {
  return kastor({
    adapter: d1(binding),
    schema: { users, posts },
    relations: ({ users, posts }) => ({
      users: { posts: many(posts) },
      posts: { author: one(users, { fields: ['authorId'], references: ['id'] }) },
    }),
  })
}

export default {
  async fetch(request, env): Promise<Response> {
    const db = createDb(env.DB)
    const url = new URL(request.url)

    if (url.pathname === '/posts') {
      const feed = await db.posts.findMany({
        where: { published: true },
        include: { author: true },
        orderBy: { title: 'asc' },
        take: 20,
      })
      return Response.json(feed)
    }
    return new Response('Not found', { status: 404 })
  },
} satisfies ExportedHandler<Env>

Do not cache the client in a module level variable keyed to one request's env. Workers reuse isolates across requests, and tying state to a single request's objects is a common source of confusing bugs. The Workers setup notes cover the same pattern for routers such as Hono.

Transactions on D1: prefer the array form

D1 does not support interactive transactions. A Worker cannot open a transaction, await a query, inspect the result in JavaScript and then commit later. What D1 offers instead is batch: a list of statements sent together and executed as one transaction, so either all of them apply or none do.

kastor maps the array form of $transaction onto one D1 batch when every query in the array compiles to a single statement. On D1, design every atomic unit as a known list of queries and use that form. Batchable queries are the reads (findMany, findFirst, findUnique, count, aggregate, groupBy, includes allowed), create without nested writes or included relations, createMany, updateMany, deleteMany, upsert and, on soft delete tables, restore and hardDeleteMany. update, delete and the OrThrow finders are not batchable, because they must fail with NOT_FOUND and a batch cannot roll back after that check; nested writes, findPage, createManyAndReturn and cursor reads are not either. Use updateMany and deleteMany with the unique where inside a batch.

// inside fetch, after const db = createDb(env.DB)
const postId = crypto.randomUUID()

await db.$transaction([
  db.posts.create({ data: { id: postId, title: 'Launch notes', authorId: 7, published: true } }),
  db.users.updateMany({ where: { id: 7 }, data: { role: 'admin' } }),
  db.posts.updateMany({ where: { authorId: 7, published: false }, data: { published: true } }),
])

If any query in the array is not batchable, the whole array falls back to a regular transaction, and that is what D1 cannot do. The callback form, db.$transaction(async (tx) => ...), throws UNSUPPORTED with a hint by default, and so does anything kastor runs inside a transaction for you, such as a create with nested writes. If your code tolerates partial writes, d1(env.DB, { transactions: 'sequential' }) runs those callbacks statement by statement with no atomicity at all; treat it as an explicit trade-off, not a default.

Since statements in a batch cannot read each other's results, generate keys in code before the batch. Here crypto.randomUUID() fills a t.uuid() primary key, so later statements could reference the new post without a round trip. When a step truly depends on data read earlier, read first, then send the writes as one batch with conditions in their where clauses so they stay correct if the data changed in between.

Migrations: generate with kastor, apply with wrangler

D1 speaks SQLite, so kastor can generate D1 migration SQL by diffing your schema against a local SQLite file. Point the config at a scratch database used only for this:

import Database from 'better-sqlite3'
import { defineConfig } from 'kastor-orm'
import { sqlite } from 'kastor-orm/sqlite'

export default defineConfig({
  schema: './src/db/schema.ts',
  adapter: () => sqlite(new Database('./.kastor/d1-shadow.db')),
  migrations: './kastor/migrations',
})

npx kastor migrate dev --name add_posts writes kastor/migrations/<timestamp>_add_posts/migration.sql and applies it to the scratch file. Wrangler expects flat numbered files in its own migrations folder, so copy the generated SQL there and apply it:

npx kastor migrate dev --name add_posts
cp kastor/migrations/*_add_posts/migration.sql migrations/0002_add_posts.sql
npx wrangler d1 migrations apply app-db --local
npx wrangler d1 migrations apply app-db --remote

Pick one tool to own the applied history. Wrangler records applied files in its own table, while kastor records them in _kastor_migrations. If both apply files to the same D1 database, each thinks the other's migrations are pending. For D1, wrangler is the practical choice, because it reaches remote databases from your terminal and CI with your Cloudflare credentials. There is a second option for local work: npx kastor-orm init --db d1 scaffolds a config whose adapter calls wrangler's getPlatformProxy() and passes the local DB binding to d1(), so kastor commands such as db push and studio run against the same local database wrangler dev uses. D1 has no transactions for DDL either, so kastor applies migration statements there one by one. Read every generated file before applying it remotely, and see the migrations guide for rename handling and review tips.

Local development with wrangler dev

npx wrangler dev runs your Worker locally with a local D1 database stored on disk under the .wrangler folder. Apply migrations with --local first, and load test data with npx wrangler d1 execute app-db --local --file=./seed.sql. Your laptop never touches production data, and you can delete the folder to start over. Pass --remote to wrangler commands only when you deliberately want the real database.

Because the local database is real SQLite, results match production closely. The scratch file used for migrations is ordinary SQLite as well, so a feature D1 restricts can still pass locally; test new kinds of SQL against a preview database before relying on them.

Errors look the same locally and in production. When a statement inside a batch breaks a constraint, D1 rolls back the whole batch and kastor throws a KastorError whose code names the cause, for example UNIQUE_VIOLATION for a duplicate email. Check it with isKastorError in your handler and return a 409 response instead of a generic 500. The hint property carries a short suggested fix, which is useful in development logs while you iterate with wrangler dev.

Limits worth knowing

D1 has limits that ordinary SQLite does not. Cloudflare publishes the current numbers in the D1 documentation, and they change over time, so check them there. Qualitatively:

  • Database size is capped per database. D1 is designed for many smaller databases, for example one per tenant, rather than one huge one.
  • Bound parameters per statement are capped at 100, far below local SQLite. The D1 dialect knows this: it splits createMany rows and long in lists into chunks that fit, so a large import becomes several statements. Splitting very large imports into several batches yourself is still a safe habit.
  • Integers come back as doubles. D1 returns every number as a JavaScript double, so the dialect reads t.bigint() columns as text and returns them as bigint, and values past 2^53 keep every digit.
  • Queries run one at a time per database. Short indexed queries keep throughput high; a slow full scan delays every request behind it. Declare indexes with index() in the table options.
  • Query duration and batch size are bounded, and Workers have their own CPU time limits. Paginate with findPage instead of loading whole tables.

If you need a SQLite family database reachable outside Workers too, compare D1 with Turso and libSQL, which use the same kastor schema. Open the playground to see the exact SQL kastor sends for each query.
