GUIDE 13From Rails Active Record

Coming from Rails and Active Record

kastor is a TypeScript ORM that runs in Node.js, Bun, Deno and edge runtimes. It does not run in Ruby and it does not replace Active Record inside a Rails app. This guide maps what you know from Active Record to kastor, for a service that moves to TypeScript or an API that shares the Rails database.

#Where kastor fits for a Rails team

Active Record is woven into Rails and written in Ruby. kastor is a TypeScript library that runs in JavaScript runtimes: Node.js, Bun, Deno and edge platforms such as Cloudflare Workers. There is no gem, and kastor cannot be called from a Rails app.

What it offers someone coming from Rails Active Record is a familiar shape in TypeScript: tables with associations, scopes as reusable conditions, eager loading, schema migrations and seeds. Two paths lead here:

  • Path A: moving to TypeScript. A service or a whole backend moves to Node.js or Bun, and the team wants the Active Record habits to carry over.
  • Path B: TypeScript next to Rails. Rails keeps running, and a TypeScript API, worker or Next.js app uses the same PostgreSQL or MySQL database.

#Step 1: pull the schema Rails built

db pull plays the role of db/schema.rb in reverse: it reads the live database and writes TypeScript. Rails tables are plural and snake case, so the exports come out as users, posts and postsTags style names, and columns keep their database names through .map().

Rails has_and_belongs_to_many join tables have no primary key. kastor declares one over both columns in the schema; if you let kastor own migrations later, add the matching constraint, which also stops duplicate pairs.

#Step 2: pick the migration owner

Rails tracks applied versions in schema_migrations, kastor in _kastor_migrations. While Rails is the main app, keep rails db:migrate as the only way to change the schema and run npx kastor db pull after each migration. When TypeScript takes over, record a baseline and switch:

Rails validations run in Ruby before a save. kastor checks types at compile time and leaves value rules (presence, length, format) to your input validation layer and to database constraints. Validate request bodies at the API boundary, and let t.string(200) and NOT NULL in the database back that up; violations come back as KastorError with codes such as NOT_NULL_VIOLATION and a hint.

#Step 4: seeds, factories and callbacks

Callbacks such as before_save and after_commit have no counterpart. Put them in the function that writes, after the await for after commit work, so readers see every side effect. dependent: :destroy runs in Ruby; in kastor, use onDelete: 'cascade' on the reference when kastor owns migrations, or delete children explicitly inside a $transaction.

#Path B in practice: sharing the database with Rails

  • Timestamps. Rails sets created_at and updated_at. With defaultNow() and .updatedAt() on those columns, kastor writes do the same.
  • Enums. Integer enums mean nothing without the Ruby mapping. Keep a shared constant like PostStatus above, or move to string enums on both sides.
  • Counter caches. Columns such as comments_count are maintained by Rails callbacks. Update them in the same transaction when TypeScript inserts or deletes children.
  • Sessions and Devise. Rails cookies are encrypted with secret_key_base. Share authentication through tokens or an auth service rather than decoding cookies in Node.
  • Connections. Puma threads and the Node pool both hold connections, so size them together.

#Pitfalls to check

  • Polymorphic associations. commentable_type plus commentable_id has no database foreign key. Filter on both columns, or use $sql.
  • STI. Single table inheritance keeps a type column; model it as a string column and filter on it.
  • Default scopes. kastor applies nothing implicitly except soft delete filtering on tables you declare with softDelete. Gems like paranoia or discard map to that option.
  • Big integer ids. Rails uses bigint keys, which arrive as bigint in TypeScript. Serialize them with String(id) in JSON responses.

Continue with the Hono or Express guide for the API itself, or the migration hub for the other paths.

#Questions people ask

Q1Can I use kastor in a Ruby or Rails project?

No. kastor runs only in JavaScript runtimes such as Node.js, Bun, Deno and Cloudflare Workers. Rails keeps Active Record. kastor is for TypeScript code that moves out of Rails or runs next to it on the same database.

Q2What is the kastor equivalent of includes and preload?

include. Post.includes(:author, :tags) becomes db.posts.findMany({ include: { author: true, tags: true } }), loaded in one statement per call with JSON aggregation, so there is no preload versus eager_load choice to make.

Q3How do Active Record scopes translate?

As typed where objects or small functions that return one. scope :published, -> { where(published: true) } becomes a constant you spread into where, and chaining scopes becomes combining objects or using AND.

Q4Can Rails and a Node.js service share a PostgreSQL database?

Yes. Run npx kastor db pull, keep one side in charge of migrations, and follow Rails conventions on the TypeScript side: set updated_at on writes and keep enum integers or strings in the same format Rails uses.

Q5What replaces db/seeds.rb and FactoryBot?

A seed file with defineSeed run by npx kastor db seed, and factory(db.users, ({ seq }) => data) for test records.
