GUIDE 18From Mongoose

Migrate from Mongoose to kastor

kastor runs on MongoDB through the official driver, with the same schema and query API it uses on SQL. Moving from Mongoose keeps your collections, your ObjectIds and your documents, and replaces populate with include pipelines that load in one round trip.

#Same database, different layer

Mongoose wraps every document in a model instance with change tracking, getters, middleware and save(). kastor takes the opposite approach on MongoDB, as it does on SQL: a schema in TypeScript, plain objects in and out, and queries compiled to aggregation pipelines. When you migrate from Mongoose, your collections and documents stay exactly as they are; you change how the application reads and writes them.

Two practical wins drive most moves. Results are typed from the schema without the HydratedDocument and InferSchemaType gymnastics, and relations load with one aggregate call per query instead of one query per populated path.

#Step 1: install kastor and connect the driver

Mongoose bundles the mongodb driver; kastor uses the one you install. Connect a MongoClient to the same URL and pass its Db to the adapter. You can also reuse Mongoose's own connection during the move: mongoose.connection.getClient() returns the driver client.

#Step 2: Mongoose schemas become table()

npx kastor db pull reads each collection's validator and indexes, or samples documents when there is no validator, and writes a starting schema. Mongoose rarely sets validators, so expect sampled types: fields missing from some documents become nullable and nested values become t.json(). Tidy the result by hand using your Mongoose schema as the reference.

A few details make the two line up. Mongoose pluralizes model names into collection names, so model('User') lives in users. The ref field is called author in the documents, so the kastor column keeps that stored name with .map('author') and frees the name author for the relation. With the default mongodb(db) ids, t.id() keys and every column that references one are typed as string: the ObjectId as hex. The t.int() on the reference only matters on SQL.

#Step 3: baseline the collections

kastor migrations on MongoDB are JSON database commands: create a collection with a $jsonSchema validator, create indexes, rename or unset fields. Your collections already exist, so record them as the starting point:

The baseline is marked as applied without running, so no validator is added to live collections behind your back. When you later want validators, which reject documents that break the schema, add them in a reviewed migration after checking that existing documents pass. Mongoose builds indexes at startup with autoIndex; turn that off before the switch so index changes go through migrations only.

For pipeline stages kastor does not model, such as $geoNear or Atlas Search, keep calling the driver directly on the same Db. That is the MongoDB counterpart of raw SQL, since $sql does not exist on MongoDB.

#Step 5: middleware, virtuals and methods

Mongoose middleware (pre('save'), post('findOneAndUpdate')) runs hidden code around operations. kastor has no hooks: put the logic in the function that writes, where it is visible and typed. Virtuals become plain functions over the row type, and instance methods become functions in a module:

When nothing imports a model any more, uninstall mongoose. Keep the mongodb driver, which kastor uses.

#Pitfalls to check

  • Missing fields versus null. Mongoose leaves unset fields out of the document. kastor writes null for nullable columns you leave out, and its null filters match missing fields too, so mixed collections work, but code that checks 'name' in doc will see the difference.
  • The __v field. Mongoose adds a version key. Leave it out of the kastor schema and it is simply ignored on reads; drop it later with a migration if you like.
  • Casting. Mongoose casts '42' to a number and strings to ObjectIds silently. kastor's types reject the wrong type at compile time, and the adapter converts id strings to ObjectIds for you.
  • Cascades. MongoDB has no foreign keys. kastor emulates onDelete for its own writes; data written by other programs is not checked.
  • Discriminators. A collection holding several shapes with a kind field maps to one table with an enum column and nullable fields per shape, or to several tables if you can split the data.

The MongoDB guide covers ids, $lookup includes and transactions in depth.

#Questions people ask

Q1Can kastor read documents written by Mongoose?

Yes. Both use the official driver and BSON. A t.id() key maps to _id and is read as the ObjectId hex string, and fields declared with .references() to it are stored as ObjectIds, which is how Mongoose stores refs.

Q2What replaces populate?

include. Post.find().populate('author') becomes db.posts.findMany({ include: { author: true } }). kastor compiles includes to $lookup stages inside one aggregate call, instead of one extra query per populated path.

Q3How do I store embedded subdocuments?

Declare them as t.json<Shape>(). The value is stored as an embedded document or array and typed as Shape in your code. Use separate tables with relations for data you query on its own.

Q4Do I need a replica set?

Only for transactions, which MongoDB allows on replica sets and sharded clusters. Atlas is already a replica set. For local development, start a single node replica set.

Q5Is there an equivalent of lean()?

Every kastor result is already a plain object: no documents, no getters, no save(). That is what lean() gave you, without the loss of types.
