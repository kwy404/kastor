GUIDE 16From Drizzle

Migrate from Drizzle ORM to kastor

Drizzle and kastor both keep the schema in TypeScript and infer types from it, so the move is mostly vocabulary: pgTable becomes table(), operator functions become where objects, and drizzle-kit hands migrations to kastor migrate.

#What changes and what stays

If you are planning to migrate from Drizzle, you already have the hard part done: your schema lives in TypeScript, your types are inferred from it, and nothing is generated. kastor works the same way, so the move does not change how your project builds. What changes is the query surface. Drizzle gives you two APIs, a SQL shaped builder (db.select().from(users).where(eq(...))) and the relational query API (db.query.users.findMany). kastor has one object API that looks like the relational one, and covers writes, nested writes, aggregates and grouping with the same shapes.

Your database and your data stay where they are. Nothing in this guide copies rows or recreates tables. The order is always the same: get a kastor schema that matches the live database, record it as the starting point of kastor migrations, then move queries one module at a time while both libraries run side by side.

#Step 1: install kastor next to Drizzle

kastor ships no driver, so you keep the one Drizzle already uses. A Postgres project keeps pg (or postgres), a SQLite project keeps better-sqlite3, a Turso project keeps @libsql/client.

init writes kastor.config.ts, a starter schema at src/db/schema.ts, a seed file and a .env with DATABASE_URL. Point that variable at the same database drizzle.config.ts uses. If your Drizzle schema already lives in src/db/schema.ts, pick another path for kastor, for example src/db/kastor-schema.ts, in the config's schema field until the move is done.

#Step 2: get a kastor schema from the database

You could translate the Drizzle schema by hand, and the mapping table below shows how. The faster way is to let kastor read the database that drizzle-kit created: db pull introspects tables, columns, defaults, indexes and foreign keys and writes a TypeScript file with every table, a schema object and a relations function guessed from the foreign keys.

#Step 3: adopt the database with a baseline

Drizzle records applied migrations in its own table (__drizzle_migrations) and journal. kastor does not read that history. It starts from a baseline instead: one migration that describes the database exactly as it is today, recorded as applied without being run.

migrate status should list the baseline as applied and nothing pending. The last command is a safety check against a copy of the database: if the pulled schema matches, kastor reports that the database is already in sync and writes no file. If it writes a file, read it, because it shows where the schema file and the database disagree. Run the baseline once per environment (development, staging, production) before the first migrate deploy there.

Note

Pick one owner for schema changes during the move. Until you remove drizzle-kit, keep generating migrations with it and run db pull again afterwards; once kastor owns migrations, stop running drizzle-kit entirely so the two never fight over the same tables.

#Step 4: one client, sharing the pool

Both libraries wrap a driver instance, so you can hand them the same pool. That keeps the number of open connections unchanged while both are in use.

#Step 5: rewrite queries side by side

The relational API maps almost word for word. with becomes include, columns becomes select, and operator functions become keys of the where object.

#Pitfalls to check

  • Nullability flips. A Drizzle column without .notNull() is nullable. If you translate by hand, add .nullable() to every such column, or the kastor types will promise values that can be null.
  • Names come from the database. db pull names exports after tables in camelCase. If you used the Drizzle casing option, columns come back with .map() calls; that is correct, keep them.
  • Timestamps and numerics. Drizzle can return timestamps as strings with mode: 'string'. kastor always returns Date for t.datetime(), a YYYY-MM-DD string for t.date() and a string for t.decimal(), so check code that formats them.
  • $onUpdate. For timestamps, use t.datetime().updatedAt(), which kastor fills on every create and update. Other computed values belong in the function that writes, or in a database trigger.
  • Prepared statements. Drizzle's .prepare() has no direct counterpart; the driver still caches statements where it supports that.
  • Two migration owners. Never run drizzle-kit push after the baseline. It would change the database behind kastor's history and the next migrate dev would try to undo it.

The Drizzle alternative guide compares the two designs in more depth, and the playground shows the SQL each kastor query compiles to on your database.

#Questions people ask

Q1Can I keep my drizzle-kit migration history?

Keep the drizzle folder in git as a record, but let kastor start from a baseline. npx kastor migrate baseline --name init writes one migration that matches the live database and marks it applied, so migrate deploy never replays the Drizzle files. New changes after that come from npx kastor migrate dev.

Q2Does kastor have an equivalent of Drizzle relational queries?

Yes. db.query.users.findMany({ with: { posts: true } }) becomes db.users.findMany({ include: { posts: true } }). Nested includes take their own where, orderBy and take, and load in one statement per call through JSON aggregation.

Q3Can Drizzle and kastor run on the same database at the same time?

Yes. Both are thin layers over your driver. You can even pass the same pg.Pool to both, which keeps the connection count where it was while you move modules one by one.

Q4Is there a replacement for the eq, and, or helpers?

kastor uses plain objects: eq(users.email, x) is { email: x }, and(a, b) is two keys in one object or AND: [a, b], or() is OR and inArray is { in: [...] }. For anything else, the sql tag works inside where.

Q5Do I lose the SQL like builder?

kastor has no chained select builder. Its object API covers filters, relations, aggregates and grouping, and db.$sql runs any SQL with bound parameters and a typed row. If a module is a large reporting query, it is fine to leave it on Drizzle or move it to $sql.
