GUIDE 22From Django ORM

Coming from the Django ORM

kastor is a TypeScript ORM for Node.js, Bun, Deno and edge runtimes. It does not run in Python, and it does not replace Django inside a Django project. It does give Django developers a familiar model of the world in TypeScript, and it can work on the same database as a running Django app.

#What kastor is, and is not, for a Django team

The Django ORM is part of Django, written in Python, and it works best inside a Django project. kastor is written in TypeScript and runs in Node.js, Bun, Deno and edge runtimes such as Cloudflare Workers. There is no Python package, and nothing in this guide makes kastor run inside Django.

So the useful question for someone coming from the Django ORM is narrower: when you write TypeScript, what does the familiar workflow look like? Teams end up here on one of two paths:

  • Path A: a service moves to TypeScript. A real time feature, an edge API or a whole backend is rewritten in Node.js or Bun, and the team wants models, relations, QuerySet style filtering and migrations it recognizes.
  • Path B: TypeScript next to Django. Django and its admin keep running, and a TypeScript API (often a Next.js or mobile backend) uses the same PostgreSQL or MySQL database.

#Step 1: pull the schema Django built

db pull reads the tables manage.py migrate created, including the many to many join tables Django generates, and writes table() definitions plus relations guessed from foreign keys. Django names tables app_model; rename the exports to something readable and keep the table names as they are.

Django enforces on_delete in Python, so its foreign keys in the database are plain constraints without a cascade rule. Check what db pull reports: if the database has no ON DELETE CASCADE, keep the reference without onDelete in kastor too, and delete children explicitly, which is what Django does for you.

#Step 2: pick the migration owner

Django records applied migrations in django_migrations; kastor uses _kastor_migrations. They never touch each other's table.

  • Django stays in charge (path B, usually). Keep using makemigrations and migrate, then run npx kastor db pull and commit the refreshed TypeScript schema. Do not run kastor migrate dev against that database.
  • kastor takes over (path A). Baseline once, then change the schema in TypeScript:

QuerySets are lazy and so are kastor queries: nothing runs until you await. A difference to keep in mind is that a kastor result never fetches more on attribute access. If you did not include a relation, it is not on the object, and the compiler tells you before the code runs. That rules out the N+1 pattern Django leaves to select_related discipline.

#Path B in practice: sharing the database with Django

  • Sessions stay in Django. Django signs session cookies and keeps sessions in its own store. Rather than decoding them, verify credentials or tokens from TypeScript.
  • Password hashes. Django's default hasher writes pbkdf2_sha256$iterations$salt$hash, which Node can check with its built in crypto module.
  • Signals. post_save receivers do not fire for TypeScript writes. Move logic that must run for every write into the database (constraints, triggers) or into one service both sides call.
  • Time zones. With USE_TZ = True, Django stores UTC. kastor returns Date objects, which are UTC instants as well.

#Pitfalls to check

  • Big auto ids. Recent Django projects use BigAutoField, so ids are t.bigId() and arrive as bigint. Older tables and auth_user may still use 32 bit ids; follow what db pull reports.
  • Generic relations. GenericForeignKey stores a content type id and an object id without a database foreign key. Query those with filters on both columns or with $sql.
  • Choices. choices= lives only in Python. If you want the same guarantee in TypeScript, declare the column as t.enum([...]); that also adds a check when kastor owns migrations.
  • Blank strings. Django stores empty strings for CharField(blank=True) without null=True. Filter on '', not null.
  • Default ordering. Meta.ordering applies implicitly in Django. kastor never orders implicitly, so add orderBy where order matters.

The Fastify and Hono guides are good next steps for an API that runs next to Django, and the migration hub lists every other path.

#Questions people ask

Q1Can kastor be used from Python or inside Django?

No. kastor runs in JavaScript runtimes only: Node.js, Bun, Deno and edge platforms. Django keeps its own ORM. kastor is for TypeScript code, either a service you move out of Django or an API that runs next to it on the same database.

Q2What is the kastor version of select_related and prefetch_related?

Both are include. Post.objects.select_related('author').prefetch_related('tags') becomes db.posts.findMany({ include: { author: true, tags: true } }), and kastor loads the whole tree in one statement per call.

Q3How do Q objects and double underscore lookups translate?

Lookups become nested filter objects: title__icontains is title: { contains, mode: 'insensitive' }, author__name is a filter on the author relation, and Q(a) | Q(b) is OR: [a, b].

Q4Can Django and a Node.js API share one PostgreSQL database?

Yes. Pull the schema with npx kastor db pull, keep one side in charge of migrations, and keep Django conventions such as the app_model table names and timestamp columns. Verify users through password hashes or tokens rather than Django session cookies.

Q5What replaces fixtures and factory_boy?

A seed file with defineSeed, run by npx kastor db seed, and the factory() helper for test data typed from the schema.
