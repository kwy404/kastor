GUIDE 11From Laravel Eloquent

Coming from Laravel and Eloquent

kastor is a TypeScript ORM. It runs in JavaScript runtimes such as Node.js, Bun, Deno and Cloudflare Workers, and it does not run inside PHP. If you know Eloquent, this guide covers the two paths that make sense: moving a Laravel service to TypeScript, or running a TypeScript API next to your Laravel app on the same database.

#The honest part first: two runtimes, two paths

Eloquent lives in PHP. kastor lives in JavaScript runtimes: Node.js, Bun, Deno, Cloudflare Workers and other edge platforms. There is no PHP extension and no bridge, and this guide will not pretend otherwise. If your whole product is a Laravel monolith and you are happy with it, Eloquent is the right tool there.

Developers coming from Laravel Eloquent usually reach for kastor in one of two situations, and the guide covers both:

  • Path A: moving to TypeScript. A team rewrites a Laravel app or splits a service out into Node.js or Bun, and wants an ORM that feels familiar: models, relations, eager loading, scopes, migrations, seeders and factories.
  • Path B: TypeScript next to PHP. Laravel keeps running, and a new TypeScript API (a mobile backend, a real time service, a Next.js frontend with server code) reads and writes the same database.

Both start the same way: kastor reads the database Laravel built.

#Step 1: pull the schema Laravel migrations built

In a new TypeScript project, install kastor and the driver for your database. Most Laravel apps run MySQL or MariaDB, so that is the example here; PostgreSQL works the same with pg.

Before the pull, set DATABASE_URL in the .env that init wrote to the Laravel database, for example mysql://forge:secret@127.0.0.1:3306/laravel. db pull then introspects tables, columns, defaults, indexes and foreign keys created by php artisan migrate, and writes table() definitions with relations guessed from the keys. Laravel uses snake case columns, so the pulled schema keeps database names with .map() while your TypeScript reads camelCase. Here is a Laravel migration and model next to the kastor schema:

Laravel's $table->id() is an unsigned big integer, so ids are t.bigId() and come back as JavaScript bigint. That is exact for every value MySQL can hold. If you prefer numbers in JSON responses, convert at the edge with Number(id) for ids you know stay small.

#Step 2: decide who owns migrations

On path A, kastor takes over. Record the current database as the first kastor migration, then make every change in src/db/schema.ts:

On path B, keep Laravel as the owner while PHP is the main application. Run php artisan migrate as before, then npx kastor db pull to refresh the TypeScript schema and commit it with the change. Never run kastor migrate dev against that database while Laravel owns it, or the two histories drift apart. Later, when the TypeScript side becomes primary, baseline and switch owners in one step.

Note

Laravel keeps its history in the migrations table and kastor in _kastor_migrations. They never touch each other's table, so switching owners later is safe.

Eager loading is where kastor feels closest to Eloquent, with one improvement: with() runs one extra query per relation, while kastor loads the whole include tree in one statement per call.

Model events and observers have no counterpart. Put that logic in the function that writes, where TypeScript checks it. Accessors such as getFullNameAttribute become plain functions over the row type.

#Path B in practice: sharing the database with Laravel

When PHP and TypeScript write the same tables, the TypeScript side has to follow the conventions Eloquent applies for you:

  • Timestamps. Eloquent fills created_at and updated_at. In kastor, defaultNow() fills the first on create and .updatedAt() fills the second on every create and update, so TypeScript writes keep the same convention.
  • Soft deletes. Declare softDelete: 'deletedAt' on tables that use the trait, so TypeScript reads skip trashed rows exactly like Eloquent does.
  • Casts. A column cast to array holds JSON text. Declare it as t.json<Shape>() and write the same shape PHP expects.
  • Auth. Laravel sessions are encrypted with APP_KEY and are hard to share. Tokens are easier: Sanctum stores a SHA-256 hash of each personal access token, so the TypeScript API can verify the tokens Laravel issues.
  • Connections. PHP-FPM workers and the Node pool both hold connections. Keep their sum under the server's max_connections.

#Pitfalls to check

  • Morph relations. morphTo and morphMany store a class name and an id without a foreign key. kastor relations need real keys, so query those with a filter on the type column, or with $sql.
  • Tinyint flags. On MySQL, Laravel booleans are tinyint(1). Check that the pulled schema typed them as t.boolean() and fix any that came back as integers.
  • Password hashes. Laravel writes bcrypt hashes with the $2y$ prefix. Check that the Node bcrypt library you pick accepts it before porting logins.
  • Enum columns. PHP enums are often stored as strings. Use t.enum([...]) with the same values so both sides agree.
  • Time zones. Laravel stores timestamps in the app time zone, usually UTC. Make the Node process and the driver use the same zone.

Once the TypeScript service is running, the Express, Fastify and AdonisJS guides show where the client lives in each framework. AdonisJS in particular will feel familiar to Laravel developers.

#Questions people ask

Q1Can I use kastor inside a Laravel or PHP project?

No. kastor is a TypeScript library and runs in JavaScript runtimes: Node.js, Bun, Deno and edge platforms such as Cloudflare Workers. A PHP application keeps using Eloquent. What you can do is run a TypeScript service next to Laravel on the same database, or move a service to TypeScript.

Q2Can Laravel and a Node.js API share one database?

Yes. Run npx kastor db pull against the Laravel database to get a typed schema, pick one side to own migrations, and make the TypeScript side respect Laravel conventions: created_at and updated_at, deleted_at for soft deletes and the same JSON shapes for cast columns.

Q3What is the kastor equivalent of Eloquent with()?

include. Post::with(['author', 'tags'])->withCount('comments') becomes db.posts.findMany({ include: { author: true, tags: true, _count: { select: { comments: true } } } }), loaded in one statement per call.

Q4Are there seeders and factories?

Yes. A seed file exports defineSeed(async (db) => ...) and runs with npx kastor db seed. factory(db.users, ({ seq }) => data) builds and creates test rows, and npx kastor migrate reset plays the role of migrate:fresh --seed.

Q5Will kastor read my Laravel migrations folder?

No. It reads the database those migrations built. db pull produces the TypeScript schema, and migrate baseline records the current state if you want kastor to own future changes. Laravel's migrations table is left alone.
