Next.js com PostgreSQL: configurando um ORM tipado no App Router

Usar Next.js com PostgreSQL fica simples quando o acesso ao banco mora no servidor e um único cliente é reaproveitado. Este guia monta tudo com o kastor e o driver pg: cliente, server components, server actions, route handlers, provedores gerenciados e migrações no deploy.

#Next.js com PostgreSQL: onde o banco entra no App Router

No App Router, o código roda em dois lugares: no servidor e no navegador. O banco só pode ser acessado do servidor. Isso deixa três pontos de entrada naturais para consultas: server components para ler dados ao renderizar, server actions para gravar a partir de formulários e route handlers para expor uma API HTTP.

Os três importam o mesmo módulo de banco. A regra principal de uma configuração de Next.js com PostgreSQL é essa: um único cliente, criado uma vez e reaproveitado. O resto do guia mostra como chegar lá com o kastor, um ORM em TypeScript que não precisa de etapa de geração e usa o driver pg que você mesmo instala.

#Instalação e variáveis de ambiente

Instale o kastor, o driver pg, o pacote server-only e o dotenv para a CLI ler o mesmo arquivo de ambiente que o Next.js:

Coloque a string de conexão em .env.local, que o Next.js carrega automaticamente e que não deve ir para o repositório. Use o nome DATABASE_URL sem o prefixo NEXT_PUBLIC_: variáveis com esse prefixo são embutidas no JavaScript enviado ao navegador, e a senha do banco nunca deve chegar lá.

O init escreve o kastor.config.ts, um src/db/schema.ts inicial com users e posts, um src/db/seed.ts e um .env com DATABASE_URL. A CLI do kastor roda fora do Next.js e, sozinha, lê só esse .env ao lado do config, sem sobrescrever variáveis que já existem. Ela não lê .env.local, então carregue esse arquivo no kastor.config.ts. Como o .env é lido antes do config, uma variável definida nos dois arquivos fica com o valor do .env na CLI: defina cada string de conexão em um só deles. #Um único cliente reaproveitado com globalThis

Em desenvolvimento, o Next.js recarrega módulos a cada alteração. Se o módulo do banco criar um pg.Pool no topo do arquivo, cada recarregamento abre um pool novo, e em pouco tempo o PostgreSQL recusa conexões. A solução conhecida é guardar o cliente em globalThis, que sobrevive aos recarregamentos:

O import 'server-only' faz o build falhar se algum componente de cliente importar esse módulo por engano. É uma proteção barata contra vazar código de banco para o navegador. Em produção, o próprio cache de módulos do Node garante uma instância por processo.

Não chame db.$disconnect() ao fim de cada requisição: o pool existe justamente para manter conexões abertas entre requisições. Reserve o $disconnect para scripts avulsos, como seeds e tarefas de manutenção, que precisam encerrar o processo quando terminam.

#Lendo dados em server components

Server components podem ser funções assíncronas, então a consulta fica direto no componente. Não há API intermediária, e o tipo de posts vem inferido do schema e do include:

Dois detalhes importam aqui. Primeiro, uma página que não usa cookies, headers nem parâmetros dinâmicos pode ser renderizada de forma estática no build, o que exigiria acesso ao banco durante o build e congelaria os dados. Declare dynamic = 'force-dynamic' ou use revalidate com um número de segundos, conforme a página.

Segundo, busque os dados relacionados no componente pai com include. Se cada item da lista for um componente que faz a própria consulta, você cria um problema N+1 sem perceber. O guia sobre consultas N+1 explica o padrão e a correção.

Se o mesmo dado aparece no layout e na página, por exemplo o usuário logado, coloque a busca em uma função própria envolvida com cache do React. Durante uma mesma requisição, chamadas repetidas com os mesmos argumentos reaproveitam o resultado em vez de consultar o banco de novo. Fora da requisição, nada fica guardado, então não há risco de mostrar dados de outro usuário.

Server actions recebem o FormData do formulário e rodam no servidor. Depois de gravar, chame revalidatePath para que a página mostre o dado novo:

Use a ação com action em um elemento form. Para devolver mensagens de erro à interface, combine a ação com useActionState do React e trate erros com isKastorError: o code UNIQUE_VIOLATION, por exemplo, vira uma mensagem amigável sem depender do texto do driver. Lembre que uma server action é um endpoint público: valide a entrada e confira a permissão do usuário dentro dela.

#Neon, Supabase e Vercel Postgres

Os provedores gerenciados falam o protocolo do PostgreSQL, então todos funcionam com o mesmo pg.Pool e o adaptador postgres(). O que muda é qual string de conexão usar.

  • Neon oferece uma string com pooler e outra direta. Use a com pooler em DATABASE_URL para a aplicação e a direta em DIRECT_URL para as migrações. As branches do Neon são úteis para dar um banco separado a cada preview.
  • Supabase também expõe uma conexão via pooler e uma conexão direta. A lógica é a mesma: pooler para a aplicação em ambiente serverless, conexão direta para a CLI.
  • Vercel Postgres, pela integração do marketplace, injeta as variáveis de conexão no projeto. Aponte DATABASE_URL para a variável com pooler.

Em qualquer provedor, lembre que cada instância serverless mantém o próprio pool. Com dez instâncias e max: 5, são até cinquenta conexões. Mantenha o max baixo e confie no pooler do provedor para o resto.

#Migrações no deploy

Em desenvolvimento, altere o schema e rode npx kastor migrate dev --name descricao. Faça commit da pasta kastor/migrations. No deploy, quem aplica as mudanças é o npx kastor migrate deploy, que só executa migrações pendentes e nunca gera SQL novo.

O lugar mais seguro para ele é uma etapa do CI que roda antes de publicar a nova versão. Se preferir manter tudo na Vercel, dá para usar o script de build kastor migrate deploy && next build. Nesse caso, garanta que deploys de preview apontem para outro banco, ou eles vão migrar o banco de produção. O guia de migrações de banco de dados cobre renomeações e o padrão expandir e contrair para mudanças sem downtime.

Para outros frameworks, veja a página de frameworks, e para conhecer o resto da API, o guia de ORM para TypeScript.

#Perguntas frequentes

Q1Como conectar o Next.js ao PostgreSQL?

Instale o driver pg e o kastor, crie um pg.Pool com a variável DATABASE_URL e passe para o adaptador postgres(). Guarde o cliente em globalThis em desenvolvimento para não abrir um pool novo a cada recarregamento.

Q2Por que o Next.js abre conexões demais com o banco?

Em desenvolvimento, o hot reload reavalia os módulos e cada avaliação pode criar um pool novo. Em produção serverless, cada instância da função tem o próprio pool. Reaproveite o cliente via globalThis e mantenha o max do pool baixo.

Q3Posso consultar o banco direto em um server component?

Sim. Server components rodam só no servidor, então podem fazer await db.posts.findMany() diretamente. Importe server-only no módulo do cliente para que o build falhe se alguém tentar usá-lo em um componente de cliente.

Q4O kastor funciona com Neon, Supabase e Vercel Postgres?

Sim, todos falam o protocolo do PostgreSQL. Use a string de conexão do provedor em um pg.Pool, de preferência a versão com pooler para a aplicação e a conexão direta para as migrações.

Q5Onde rodar as migrações em um projeto Next.js na Vercel?

O mais seguro é uma etapa do CI que roda npx kastor migrate deploy antes de publicar. Outra opção é incluir o comando no script de build. Veja o guia de migrações de banco de dados.
