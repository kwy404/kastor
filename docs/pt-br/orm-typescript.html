GUIA 01ORM para TypeScript

ORM para TypeScript: como escolher e como usar o kastor do schema às migrações

Um bom ORM para TypeScript deixa o compilador conferir cada consulta sem pedir uma etapa de geração de código. Este guia mostra o que avaliar antes de escolher e percorre o kastor do table() até o migrate deploy.

#O que é um ORM para TypeScript

Um ORM (mapeamento objeto relacional) traduz chamadas de função em consultas ao banco e devolve objetos comuns. Em JavaScript puro isso já economiza muito SQL repetido. Em TypeScript o ganho é maior: o compilador sabe quais colunas existem, quais podem ser nulas e qual formato cada consulta devolve.

Na prática, um ORM para TypeScript bem feito resolve três problemas. Primeiro, erros de digitação em nomes de coluna aparecem no editor, não em produção. Segundo, o formato do resultado muda junto com o select e o include, então você não precisa declarar interfaces à mão. Terceiro, o histórico do schema fica versionado em migrações, e não espalhado em scripts soltos.

Um ORM não substitui saber SQL. Ele cuida do trabalho repetitivo (CRUD, relações, paginação, transações) e deixa você livre para escrever SQL à mão onde isso realmente faz diferença. Os melhores resultados vêm de usar as duas coisas no lugar certo.

O que separa um ORM de outro são as escolhas de projeto: onde o schema mora, como os tipos nascem, quantos bancos são suportados e o que acontece quando você precisa sair da abstração.

#O que avaliar antes de escolher

Antes de adotar qualquer ferramenta, passe por esta lista. Ela vale para o kastor e para qualquer alternativa.

  • Tipos inferidos sem etapa de geração. Alguns ORMs usam uma linguagem de schema própria e um comando de geração que cria o cliente tipado. É um trade-off legítimo, mas exige lembrar de rodar o comando e lidar com arquivos gerados no CI. Quando o schema é TypeScript, os tipos acompanham cada alteração na hora.
  • Vários bancos com a mesma API. Se o projeto pode trocar de PostgreSQL para SQLite nos testes, ou se a empresa tem SQL Server e Oracle legados, conta muito ter a mesma API de consultas em todos.
  • Migrações de verdade. Arquivos SQL versionados, um comando para aplicar em produção e detecção de renomeações para não perder dados por acidente.
  • Sem N+1. Carregar relações não pode disparar uma consulta por linha. Veja o guia sobre consultas N+1 para entender o custo.
  • SQL puro quando precisar. Relatórios, CTEs e funções específicas do banco sempre aparecem. A saída para SQL precisa ser segura contra injeção e, de preferência, tipada.
  • Erros legíveis. Uma violação de unicidade deveria virar um código estável que você trata com if, não uma string do driver que muda entre bancos.

O kastor foi desenhado em cima dessa lista: schema em TypeScript, nenhum binário de engine, nenhuma linguagem de schema, adaptadores para PostgreSQL, CockroachDB, MySQL, MariaDB, SQLite, libSQL (Turso), Cloudflare D1, SQL Server, Oracle e MongoDB.

#Instalação e schema

O kastor não traz drivers embutidos. Você instala o pacote e o driver do seu banco, e o adaptador recebe a instância pronta. Isso deixa pool, TLS e versão do driver sob seu controle.

O init pergunta qual banco você usa (ou recebe --db postgres) e cria o kastor.config.ts, que aponta para o arquivo de schema, para a pasta de migrações e para o seed. Ele também escreve um src/db/schema.ts inicial, um src/db/seed.ts e um .env com DATABASE_URL, que a CLI lê da pasta do config. O schema é um módulo TypeScript comum, com uma chamada table() por tabela:

Repare nos tipos que saem daí: createdAt vira Date, name vira string | null e role vira a união 'user' | 'admin'. Em InferInsert, colunas com default ficam opcionais. Se a tabela já tem nomes de coluna em snake_case, use .map('created_at') e mantenha camelCase no código.

#Cliente e relações

O cliente junta adaptador, schema e relações. As relações não criam colunas: elas só dizem ao kastor como ligar tabelas que já têm chave estrangeira.

Para trocar de banco, troque apenas a linha do adaptador. Com SQLite seria sqlite(new Database('app.db')) usando better-sqlite3; com MySQL, mysql(pool) com um pool do mysql2/promise. Schema, relações e consultas continuam iguais.

#Consultas tipadas no dia a dia

Cada tabela vira um modelo em db, com métodos como findMany, findUnique, create, update, upsert, count e groupBy. Os argumentos seguem um padrão previsível: where, select, include, orderBy, take, skip.

O tipo de authors já inclui posts com apenas id e title. Se você remover o select, o tipo cresce sozinho. Esse é o ponto central de um ORM para TypeScript: o formato da resposta segue a consulta.

Duas propriedades valem a pena conhecer. As consultas são preguiçosas: nada roda até o await, e query.toSQL() devolve as instruções sem executar. E os includes aninhados carregam em uma única consulta por chamada raiz em todos os adaptadores SQL, que montam as relações com agregação JSON; no MongoDB eles viram estágios $lookup de uma única agregação. Para ver o SQL exato de cada banco, abra o playground.

#Migrações: do schema ao banco

Quando o schema muda, a CLI compara o TypeScript com o banco ao vivo, escreve um arquivo SQL versionado e o aplica. Em produção, outro comando aplica só o que está pendente.

O migrate dev cria kastor/migrations/<timestamp>_add_posts/migration.sql. Se você renomeou uma coluna, ele pergunta se é uma renomeação em vez de apagar e recriar; fora de um terminal interativo, passe a resposta com --rename users.name:fullName. Faça commit da pasta de migrações junto com o código. O migrate deploy roda no CI ou na etapa de release, nunca o migrate dev.

Para protótipos, db push sincroniza o schema sem criar arquivo. Para bancos que já existem, db pull gera o schema em TypeScript. O guia de migrações de banco de dados detalha cada caso, inclusive mudanças destrutivas seguras.

Nota

Rode npx kastor doctor quando algo não conectar. Ele confere o arquivo de configuração, a conexão, as migrações pendentes e diferenças entre o schema e o banco antes de você perder tempo depurando.

#SQL puro e tratamento de erros

Nem tudo cabe na API de modelos, e não precisa caber. O db.$sql aceita uma template tag com tipo de retorno declarado; cada valor interpolado vira parâmetro, então não há concatenação de strings. O tipo declarado é uma promessa, não uma conferência: os valores chegam como o driver devolve, e o pg devolve count como string, por isso o ::int no exemplo.

Os erros chegam como KastorError com um code estável, como UNIQUE_VIOLATION, FOREIGN_KEY_VIOLATION ou NOT_FOUND para os métodos OrThrow. A mensagem é em inglês simples e o hint sugere a correção. Como o código é o mesmo em todos os bancos, o tratamento de erro não muda quando o adaptador muda.

#Próximos passos

Com schema, cliente e migrações no lugar, o resto é aplicação. Se você usa Next.js, o guia de Next.js com PostgreSQL mostra como reaproveitar um único cliente entre recarregamentos e como rodar migrações no deploy. Para outros frameworks, veja a página de frameworks, e consulte a referência da API para todos os filtros e opções.

Um bom teste final para qualquer ORM para TypeScript: renomeie uma coluna no schema e veja quantos erros o editor aponta antes de você rodar qualquer coisa. Se a resposta for todos, você está no caminho certo.

#Perguntas frequentes

Q1Qual o melhor ORM para TypeScript em 2026?

Depende do seu banco e do seu fluxo de trabalho. Avalie se os tipos são inferidos sem etapa de geração, quais bancos são suportados, como funcionam as migrações e se há saída para SQL puro. O kastor foca em schema em TypeScript, vários bancos com a mesma API e includes que nunca viram N+1.

Q2Preciso rodar um comando de geração para ter tipos no kastor?

Não. O schema é código TypeScript comum, então os tipos de findMany, create e dos includes são inferidos enquanto você digita. Não existe binário de engine nem linguagem de schema separada.

Q3O kastor instala o driver do banco de dados?

Não. Você instala o driver que quiser, como pg, mysql2 ou better-sqlite3, cria a instância e entrega ao adaptador. Assim você controla versão do driver, pool e configurações de TLS.

Q4Dá para usar SQL puro junto com um ORM TypeScript?

Sim. No kastor, db.$sql executa uma template tag tipada e transforma cada valor interpolado em parâmetro, e db.$execute devolve o número de linhas afetadas. Fragmentos sql também podem entrar dentro de um where.

Q5Como migrar um banco existente para um ORM TypeScript?

Rode npx kastor db pull para gerar um arquivo de schema em TypeScript a partir das tabelas atuais. Revise o arquivo, ajuste nomes e relações e a partir daí use migrate dev normalmente. Veja o guia de migrações de banco de dados.
