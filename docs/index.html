Schema and types

Write a schema, get types instantly

Tables and relations are ordinary TypeScript values. The compiler infers every result from them, so the types are already there on the next keystroke.

  • Plain TypeScript. No schema language, no extension, and your editor understands every line.
  • No generate step. Nothing to rerun after a change, nothing to forget in CI.
  • Shaped by the query. Includes add relations to the result, select narrows it.
  • Rename safely. Rename a column and every call site lights up in the editor.
src/db/schema.ts
import { table, t } from 'kastor-orm'

export const users = table('users', {
  id: t.id(),
  email: t.string(255).unique(),
  name: t.string().nullable(),
  role: t.enum(['user', 'admin']).default('user'),
  createdAt: t.datetime().defaultNow(),
})

export const posts = table('posts', {
  id: t.id(),
  title: t.string(200),
  published: t.boolean().default(false),
  authorId: t.int().references(() => users.id),
})

Nested includes in one query

Ask for authors and their latest posts and kastor sends one statement, built for the database you run. Never one query per row.

src/feed.ts
const authors = await db.users.findMany({
  where: { email: { endsWith: '@acme.com' } },
  select: {
    name: true,
    posts: {
      where: { published: true },
      orderBy: { views: 'desc' },
      take: 3,
      select: { title: true, views: true },
    },
  },
})
SELECT "t0"."name" AS "name", (
  SELECT COALESCE(json_agg("s"."j" ORDER BY "s"."rn"), '[]'::json)
  FROM (
    SELECT json_build_object('title', "t1"."title", 'views', "t1"."views") AS "j", ROW_NUMBER() OVER (ORDER BY "t1"."views" DESC) AS "rn"
    FROM "posts" "t1"
    WHERE "t1"."authorId" = "t0"."id" AND ("t1"."published" = $1)
    ORDER BY "t1"."views" DESC
    LIMIT 3
  ) "s"
) AS "posts"
FROM "users" "t0"
WHERE "t0"."email" LIKE $2 ESCAPE '!'
SELECT `t0`.`name` AS `name`, (
  SELECT COALESCE(JSON_ARRAYAGG(CAST(`s`.`j` AS JSON)), JSON_ARRAY())
  FROM (
    SELECT JSON_OBJECT('title', `t1`.`title`, 'views', `t1`.`views`, '__kastor_rn', ROW_NUMBER() OVER (ORDER BY `t1`.`views` DESC)) AS `j`
    FROM `posts` `t1`
    WHERE `t1`.`authorId` = `t0`.`id` AND (`t1`.`published` = ?)
    ORDER BY `t1`.`views` DESC
    LIMIT 3
  ) `s`
) AS `posts`
FROM `users` `t0`
WHERE `t0`.`email` LIKE ? COLLATE utf8mb4_bin ESCAPE '!'
SELECT "t0"."name" AS "name", (
  SELECT json_group_array(json("s"."j"))
  FROM (
    SELECT json_object('title', "t1"."title", 'views', "t1"."views", '__kastor_rn', ROW_NUMBER() OVER (ORDER BY "t1"."views" DESC)) AS "j"
    FROM "posts" "t1"
    WHERE "t1"."authorId" = "t0"."id" AND ("t1"."published" = ?)
    ORDER BY "t1"."views" DESC
    LIMIT 3
  ) "s"
) AS "posts"
FROM "users" "t0"
WHERE substr("t0"."email", -length(?)) = ?
SELECT [t0].[name] AS [name], COALESCE((
  SELECT TOP (3) [t1].[title] AS [title], [t1].[views] AS [views]
  FROM [posts] [t1]
  WHERE [t1].[authorId] = [t0].[id] AND ([t1].[published] = @p1)
  ORDER BY [t1].[views] DESC
  FOR JSON PATH, INCLUDE_NULL_VALUES
), '[]') AS [posts]
FROM [users] [t0]
WHERE [t0].[email] COLLATE Latin1_General_100_BIN2 LIKE @p2 ESCAPE '!'
SELECT "t0"."name" AS "name", (
  SELECT JSON_ARRAYAGG("s"."j" FORMAT JSON ORDER BY "s"."rn" RETURNING CLOB)
  FROM (
    SELECT JSON_OBJECT('title' VALUE "t1"."title", 'views' VALUE "t1"."views" NULL ON NULL RETURNING CLOB) AS "j", ROW_NUMBER() OVER (ORDER BY "t1"."views" DESC) AS "rn"
    FROM "posts" "t1"
    WHERE "t1"."authorId" = "t0"."id" AND ("t1"."published" = :1)
    ORDER BY "t1"."views" DESC
    FETCH NEXT 3 ROWS ONLY
  ) "s"
) AS "posts"
FROM "users" "t0"
WHERE "t0"."email" LIKE :2 ESCAPE '!'

Migrations

Migrations you can read

Change the schema, run one command. kastor diffs it against the live database, explains the plan in plain English and writes a SQL file you review and commit.

  • Careful by default. Warns before anything that can fail or lose data, and asks before it treats a rename as a drop.
  • Plain SQL files. One folder per migration, a header that says what changed, nothing hidden.
  • Built for CI. migrate deploy applies pending files, migrate status catches drift.
  • Existing database? db pull writes the schema from it, migrate baseline adopts it.
  • Coming from Prisma? kastor import prisma converts schema.prisma and keeps the history. See the migration guides.

Studio

See your data. Edit it. Understand the shape.

Run npx kastor studio and a local web UI opens on your machine: browse every table, filter and search, edit rows, follow foreign keys and read the diagram of the whole database.

  • Runs on 127.0.0.1 behind a private session token, with your own config.
  • Filters, text search, paging and a read only mode for data you must not touch.
  • A diagram drawn from the live schema, downloadable as SVG.

Everything else

Everything a data layer needs

12 more details. Each one is real code that runs on every supported database.

Schema in plain TypeScript

Tables, columns, indexes and relations are ordinary TypeScript values. No schema language to learn, no extension to install, and your editor already understands every line.

Types inferred as you type

There is no generate step. Change a column and every query that touches it is checked again on the next keystroke, in the editor and in CI, with nothing to regenerate.

Friendly, familiar queries

findMany, findUnique, create, update, upsert, count, aggregate and groupBy with where, select, orderBy, take, skip, cursor and distinct. Filters read like the sentence you would say out loud.

Nested includes in one query

Relations load with JSON aggregation inside a single statement on every SQL database, and as $lookup stages of one pipeline on MongoDB. Never one query per row.

Nested writes

Create a row with its children, or connect it to existing ones, in one call. kastor splits the work into single table writes inside one transaction.

Transactions, both ways

An interactive callback when one step depends on the last, or an array of queries that run together. Errors roll everything back.

Typed raw SQL

When a query is easier in SQL, write SQL. Template values become parameters, never string concatenation, and the row type is yours to declare.

Errors that tell you the fix

Driver errors become a KastorError with a stable code, a plain English message and a hint, the same on every database.

Automatic migrations

kastor diffs your TypeScript schema against the live database and writes a readable SQL file you can review and edit. A renamed column is a question, never a silent drop.

Existing database? Pull it

Point kastor at a database you already have and it writes the TypeScript schema for you, relations included, so you can start querying in minutes.

Soft delete and cursor pages

Mark a table with softDelete and deletes set a timestamp instead, filtered out everywhere, includes too. findPage returns opaque cursors for stable infinite scroll.

Seeds and test factories

A typed seed file for every environment, and factories that build valid, unique rows for tests in one line each.

FAQ

Questions people ask

Still curious? Open an issue on GitHub and Kas will take a look.

Which databases does kastor support?

PostgreSQL, CockroachDB, MySQL, MariaDB, SQLite (better-sqlite3, node:sqlite, bun:sqlite), libSQL and Turso, Cloudflare D1, SQL Server, Oracle and MongoDB, with one schema and one query API.

Does kastor need a generate step or a binary engine?

No. Types are inferred from the schema by the TypeScript compiler as you type, and queries are compiled to SQL in plain JavaScript. There is nothing to regenerate in CI and nothing native to download.

How does kastor avoid N+1 queries?

Nested includes load in one statement per root call: JSON aggregation on every SQL database and a single aggregation pipeline with $lookup stages on MongoDB. Never one query per row. See the N+1 guide.

How do I migrate from Prisma to kastor?

Run npx kastor import prisma to turn schema.prisma into a TypeScript schema, then npx kastor migrate baseline --from-prisma prisma/migrations so the migrations Prisma already applied stay recorded. Your data never moves. The Prisma migration guide maps every client call, and the migration hub covers Drizzle, TypeORM, Sequelize, Knex, Mongoose, Laravel, Django and Rails.

Can I use kastor with an existing database?

Yes. Run npx kastor db pull to introspect the live database into a TypeScript schema file, relations included, then query it right away. Migrations can take over from there when you are ready.

Which drivers does kastor install?

None. kastor ships no database drivers: you install the one you want (pg, mysql2, better-sqlite3, mssql, oracledb, mongodb and so on) and pass its instance to the adapter. Drivers are optional peer dependencies.

Does kastor work on serverless and edge runtimes?

Yes, wherever the driver works: Cloudflare Workers with D1, Turso over HTTP, Neon, Supabase and Vercel Postgres through pg compatible pools, Bun with bun:sqlite and Deno with npm specifiers. The core has no Node only imports.

Is kastor free?

Yes. kastor is open source under the MIT license, including the CLI, migrations and the studio.
