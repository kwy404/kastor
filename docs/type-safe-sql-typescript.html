GUIDE 04Type safe SQL

Type safe SQL in TypeScript, from inferred rows to raw queries

Type safety for database code covers three things: the shape of the rows you get back, the values you send in and the names you reference. This guide shows how kastor handles each one, including raw SQL with db.$sql.

#What type safe SQL in TypeScript actually means

"Type safe" gets used loosely. For database code it is useful to split it into three questions:

  • Rows: does the compiler know the exact shape of what a query returns, including which fields can be null?
  • Inputs: are the values you filter or insert checked against the column types, and are they sent as bound parameters rather than pasted into the SQL text?
  • Names: does a typo in a column or relation name fail at compile time, before a user hits it?

An ORM with an inferred schema answers all three for everyday queries. Raw SQL can only answer the second one completely, but with the right API it gets close on the first. This guide covers both, using kastor's API, so you know exactly where the compiler protects you and where it cannot.

#Inferred row types and select narrowing

Everything starts with the schema. Each column builder carries a TypeScript type: t.datetime() is a Date, t.decimal(10, 2) is a string (so no precision is lost), t.bigint() is a bigint, t.enum([...]) is a union of literals, and .nullable() adds | null.

Queries derive their result type from the arguments. Without select you get the full row. With select the type narrows to the keys you asked for, and with include each relation appears under its name with the related table's row type.

Use InferSelect and InferInsert at the edges of your app: function signatures, API handlers and test factories. Inside a function, let inference do the work and avoid writing row types by hand, because hand written types drift from the schema.

#JSON, money and big numbers

A few column types deserve attention because their TypeScript type is chosen to avoid silent data loss, and that choice shows up in your code.

  • Decimals are strings. A JavaScript number cannot hold every decimal(10, 2) value exactly, so kastor returns the string the database sent. Do money math with integer cents or a decimal library, and send strings back on insert.
  • Big integers are bigint. Columns declared with t.bigint() or t.bigId() come back as bigint. Note that JSON.stringify throws on bigint, so convert them to strings in your API layer before returning a response.
  • JSON columns use the type you declare. t.json<Settings>() types the column as Settings in queries and inserts. The database does not check that shape, so validate data from outside your app before it is stored.
  • Dates and times. t.datetime() is a Date, while t.date() and t.time() are strings such as '2026-10-13' and '14:30:00', which avoids time zone shifts for calendar dates.

These rules are the same on every adapter, so code that handles them correctly on PostgreSQL also works on MySQL, SQLite or SQL Server.

#Typed raw SQL with db.$sql

Some queries read better as SQL: reports with grouping, window functions, recursive CTEs. db.$sql is a tagged template. Every ${value} you interpolate becomes a bound parameter, sent to the database separately from the SQL text, so the database never parses it as SQL. That is what makes it safe from SQL injection, and it is why you should never build a query string by concatenation.

The type argument describes the rows. Remember that raw SQL uses database names, so createdAt is created_at here because of .map().

Be honest with yourself about what the type argument is: a declaration, not a check. kastor cannot know the shape of arbitrary SQL, so values arrive as your driver returns them. The pg driver, for example, returns count(*) as a string because it is a 64 bit integer, which is why the query casts it with ::int. Keep each raw query covered by a test that runs against a real database.

#sql fragments inside normal queries

Often you need one piece of SQL, not a whole query. The sql tag builds a fragment you can put in a where clause next to typed filters. The rest of the query, including its result type, stays the same.

Three helpers cover the rest. sql.ident quotes a table or column name, for dynamic sorting with an allowlist as above. sql.join combines a list of fragments. sql.raw inserts text without parameters: use it only for constant strings you wrote yourself, never for anything that came from a request. If you can see user input flowing into sql.raw, treat it as a security bug.

Site engineer note

Not sure what an object API query compiles to? Call .toSQL() on it to get the statements and parameters without running them (a db.$sql query is already the SQL you wrote, so it has nothing to show there), or open the playground to see the exact SQL for each database.

#A short checklist

  • Declare the schema once in TypeScript and derive types with InferSelect and InferInsert instead of writing interfaces by hand.
  • Prefer the object API for CRUD and relations: it gives you checked names, checked values and exact result types.
  • Use select to return only what a screen or endpoint needs; the type follows.
  • For raw SQL, use db.$sql with a type argument, interpolate values, cast aggregates in SQL and test against a real database.
  • Never concatenate strings into SQL and never pass request data to sql.raw.
  • Handle failures with isKastorError and the error code, which works the same on every database. See the API reference for the full list.

To see how these types work alongside relation loading, read the TypeScript ORM guide and the guide on avoiding N+1 queries.

#Questions people ask

Q1How do I get type safe SQL queries in TypeScript?

Declare your tables in TypeScript and let the query API infer row types from them, so typos and wrong value types fail at compile time. For raw SQL, use a tagged template such as db.$sql that binds every value as a parameter and takes the row type as a type argument.

Q2Does a tagged template prevent SQL injection?

Yes, when the library turns each interpolated value into a bound parameter, as db.$sql and sql do. The danger comes back when you build SQL by string concatenation or pass user input to sql.raw, so never do either.

Q3Is the row type of a raw query checked at runtime?

No. The type argument of db.$sql describes what you expect, and the values come from the driver. Cast in SQL where drivers return strings, for example count(*)::int in PostgreSQL, and keep raw queries covered by a test.

Q4What is the difference between InferSelect and InferInsert?

InferSelect is the type of a row you read, with every column present. InferInsert is the type you pass to create, where columns with defaults or nullable columns are optional.

Q5Can I use dynamic column names in raw SQL safely?

Use sql.ident, which quotes the name as an identifier, and only pass names from an allowlist you control. Values always go through normal interpolation so they become parameters.
