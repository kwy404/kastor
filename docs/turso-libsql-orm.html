GUIDE 14Turso and libSQL ORM

A Turso ORM for TypeScript, built on libSQL

kastor takes a @libsql/client client through libsql(client), so the same typed schema runs on a local SQLite file, a Turso database at the edge, or an embedded replica next to your server.

#Turso, libSQL and where kastor fits

libSQL is an open source fork of SQLite that adds a network server, replication and a few SQL extensions. Turso is the hosted service built on it. From your code, both are reached through the same driver: @libsql/client. That client accepts local file URLs, remote URLs and a hybrid mode called embedded replicas, which makes it a flexible base for an ORM.

kastor's libsql adapter takes a client you create and uses the SQLite dialect for everything else. Your schema is plain TypeScript, types are inferred as you type, and there is no generate step or engine binary, which keeps serverless bundles small. The same schema also runs on Cloudflare D1 and plain SQLite.

#Local development with file: URLs

A file: URL makes the libSQL client open a local SQLite file directly, in process. No server runs, queries are fast, and you can delete the file to start over. That is the simplest setup for development, tests and CI.

If you want to exercise the network path locally, turso dev --db-file local.db starts a local libSQL server, and you point TURSO_DATABASE_URL at the address it prints. Code that behaves well against the server, where each statement is a network request, tends to behave well against Turso too.

Keep local data separate from production. A seed file built with defineSeed and factory gives every developer the same starting rows; the seeding guide shows how.

#Embedded replicas

An embedded replica is a local SQLite file that the libSQL client keeps in sync with a remote Turso database. Reads are served from the local file, so they skip the network entirely. Writes go to the remote primary, and the client pulls changes back into the file.

Call sync() at startup so the first reads are not stale, and set syncInterval to keep pulling changes in the background. Embedded replicas need a writable, persistent filesystem, so they suit long running servers, containers with a volume and VMs. They do not suit serverless functions that start from an empty disk on each invocation. Other replicas see a write only after their next sync, so pick an interval your application can tolerate. The Turso docs explain the consistency guarantees in detail.

#Edge runtimes

Edge runtimes such as Cloudflare Workers and Vercel Edge Functions have no filesystem and limited Node.js APIs. For them, import createClient from @libsql/client/web. That build talks to Turso over HTTP with fetch, and works the same with kastor: pass the client to libsql(client). File URLs and embedded replicas are not available in that build.

On Workers, read the URL and token from env and create the client inside the request handler, the same pattern the Workers setup notes describe. Because each statement is a request to Turso, round trips matter more at the edge than anywhere else. Place the database in a region close to where most of your traffic runs, and lean on single statement includes and batched writes.

#Migrations

The CLI reads kastor.config.ts. Using the same environment variables as the app lets one config serve both local files and Turso:

During development, npx kastor migrate dev --name init diffs the schema against your local file, writes a migration and applies it. Commit the migration folder. In CI or at deploy time, set the Turso variables and run npx kastor migrate deploy to apply pending files to the remote database. npx kastor migrate status shows what is applied.

SQLite cannot alter every part of a table in place, so some changes, such as changing a column type, require rebuilding the table. Read the generated SQL before deploying it, especially on large tables. The migrations guide covers renames and review in more depth.

#One query includes and transactions

On a remote database, the number of round trips is often what makes a page slow. kastor loads nested include trees in one statement per root call on the SQLite family, using the json_group_array and json_object functions to build nested results inside the database. A list of posts with their authors and tag counts is one request to Turso, not one per post. Open the playground to see the exact SQL, and read how kastor avoids N+1 queries for the background.

Both transaction forms work with the libSQL client. The callback form, db.$transaction(async (tx) => ...), runs your reads and writes together and rolls back if the callback throws. The array form takes a fixed list of queries and is the better fit for remote databases, because it never holds a transaction open while your own code awaits something else.

SQLite allows one writer at a time, and Turso follows the same model. Keep transactions short, avoid network calls to other services inside them, and handle KastorError codes such as UNIQUE_VIOLATION with isKastorError so conflicts produce clear responses instead of generic failures.

Payload size is the other cost of a remote database. Every column you read crosses the network, so pass select with only the fields a page renders, especially for t.text() and t.json() columns that can grow large. For long lists, findPage returns a cursor you hand back for the next page, which keeps each request small and avoids the growing cost of deep skip offsets. Both habits help on a local file too, but on Turso you see the difference in response times right away.

#Questions people ask

Q1How do I connect an ORM to Turso?

Create a client with createClient from @libsql/client, passing the database url and an authToken from the Turso CLI, then pass it to libsql(client) from kastor/libsql. kastor ships no driver, so the libSQL client is the only database dependency.

Q2Can I use Turso locally without an account?

Yes. Use a file: URL such as file:local.db for a plain local SQLite file, or run turso dev for a local libSQL server. The same kastor code works against both and against Turso in production.

Q3What is a Turso embedded replica?

A local SQLite file that the libSQL client keeps in sync with a remote Turso database. Reads are served from the local file, writes go to the remote primary. You enable it with syncUrl next to a file: URL.

Q4Does Turso work on edge runtimes like Cloudflare Workers?

Yes. Import createClient from @libsql/client/web, which talks to Turso over HTTP and needs no filesystem. File URLs and embedded replicas are not available there.

Q5Does kastor load relations on Turso in one query?

Yes. On the SQLite family, nested includes compile to json_group_array and json_object subqueries, so each root call runs one statement. That matters on Turso, where every extra round trip adds network latency.
