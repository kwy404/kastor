GUIDE 21Fastify

kastor with Fastify

Fastify is built around plugins and decorators, so the database belongs in a plugin that decorates the instance with a typed client and closes the pool in the onClose hook. Routes then use app.db with types inferred from your kastor schema.

#Project structure

Fastify encapsulates plugins: a decorator added inside a plugin is only visible to that plugin's children, unless the plugin is wrapped with fastify-plugin. A database plugin should be wrapped, so the whole app shares one client.

#The plugin and its type

The plugin builds the client, decorates the instance and registers an onClose hook. The module augmentation tells TypeScript what app.db is, so routes get the full query types.

#Routes with validation

Route schemas validate input before the handler runs and speed up serialization of the response. Inside the handler, app.db is the typed client.

In tests, build the app against a test database, call app.inject(), and await app.close() in afterAll so the test runner does not hang on open connections. Migrations run before the server starts, in CI or a release step:

For development, tsx watch --env-file=.env src/server.ts restarts the process on change; the signal handler closes the old pool first.

#Why a plugin instead of a plain import

You could import the client from a module, as the Express guide does, and it would work. The plugin buys three things in a Fastify codebase. First, lifecycle: the onClose hook ties the pool to the instance, so every way of stopping the app (signals, tests, app.close() in a script) closes connections without extra code. Second, configuration: the plugin takes its options from register, so tests can build an app against a different database without touching environment variables or module mocks. Third, ordering: Fastify loads plugins in sequence and awaits each one, so the client exists before any route plugin runs.

Encapsulation is the part that surprises people. Fastify gives each plugin its own context; decorators added inside are visible to that plugin and its children only. Wrapping the database plugin with fastify-plugin opts out of that, which is right for shared infrastructure like a client. Route plugins, on the other hand, should stay encapsulated so their hooks and decorators do not leak into each other.

#Transactions inside a request

A handler that writes to several tables should do it in one transaction: app.db.$transaction(async (tx) => ...) runs every call on one connection, commits when the callback resolves and rolls back when it throws. Keep the callback free of slow work such as HTTP calls to other services, because the connection stays checked out until it returns. When the writes do not depend on each other's results, the array form, app.db.$transaction([a, b]), is shorter and holds the connection for less time.

Running Fastify on a serverless platform, for example behind an adapter on AWS Lambda, changes only the pool size. Each function instance runs one copy of the app with its own pool, so set max to 1 or 2 and put a pooler in front of the database, as the Lambda guide explains.

#Production checklist

Before the first deploy, check these points. Each one prevents a problem that otherwise shows up only under real traffic, usually as exhausted connections, a leaked secret or a schema that does not match the code that is running:

  • The database plugin is wrapped with fastify-plugin and registered before routes.
  • FastifyInstance is augmented, so app.db is typed.
  • The onClose hook disconnects the pool.
  • Routes declare body and response schemas.
  • Tests call app.close(), and CI runs migrations before release.

#Pitfalls

  • Forgetting fastify-plugin. Without it, app.db exists only inside the plugin's own scope, and sibling route plugins see undefined.
  • Response schemas and bigint. Fastify's serializer drops fields missing from a response schema and cannot write bigint. Declare the fields you return and convert big keys to strings.
  • Registering order. Register the db plugin before the routes that use it; Fastify loads plugins in order.
  • Pool size. Fastify handles many concurrent requests on one process; size max for your real concurrency and the database limit, not the request rate.

#Questions people ask

Q1How do I share a database client across Fastify plugins?

Wrap the setup in fastify-plugin so the decorator is not encapsulated, then app.decorate('db', db). Every plugin registered after it sees app.db.

Q2How do I type app.db?

Augment the FastifyInstance interface with declare module 'fastify' and set db to the type of your client. The query types then flow into every route.

Q3When should the pool close?

In an onClose hook. app.close() runs it, which happens on graceful shutdown and at the end of tests that use app.inject().

Q4Can I use Fastify's JSON schema validation with kastor?

Yes. Validate the request with a route schema; kastor then receives values the compiler and the runtime both trust. Use a type provider if you want the schema to type request.body too.
